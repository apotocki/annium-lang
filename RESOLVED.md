## `conditional_t` (plain `if`) is implemented — an earlier `FUTURE_WORK.md` entry wrongly claimed otherwise

`FUTURE_WORK.md`'s `not_empty_condition_t` entry previously also claimed `conditional_t` throws, that conditionals therefore could not compile at all, and that fixing it would require reinstating the commented-out `jt`/`jtp`/`jtn`/`jf`/`jfp`/`jfn` opcodes. All three claims were incorrect, verified by reading the file:

- The throwing `conditional_t` override in `compiler_visitor_generic` (`vm/compiler_visitor.hpp:451`) is **entirely inside an `#if 0` block** (lines 450-489) — dead code.
- The live handler is `compiler_visitor_base::operator()(semantic::conditional_t const&)` (`vm/compiler_visitor.hpp:241`), a real implementation. Both `compiler_visitor` and `inline_compiler_visitor` inherit it through `using compiler_visitor_base::operator();`, so *both* codegen paths have it.
- It emits `asm_builder_t::op_t::je`/`jne`/`jmp` against labels from `fnbuilder_.make_label()` — the `asm_builder` layer, resolving to the live `jmp`/`je`/`jne` opcode family. It never touches `append_jtx`/`append_jfx`, so the commented-out `jt`/`jf` opcodes are irrelevant to it and do **not** need reviving.
- `switch_t` (`vm/compiler_visitor.hpp:289`) is implemented the same way.

The mistake came from grepping for `THROW_NOT_IMPLEMENTED_ERROR` near `conditional_t` without checking whether the enclosing block was `#if 0`'d — exactly the trap `IMPLEMENTATION_NOTES.md` warns about under "Stale / dead code caveat". (`not_empty_condition_t` itself is still not implemented — that part of the original entry was correct and remains open in `FUTURE_WORK.md`.)

## `ref(T)` item 2 — struct fields are referenceable too (tuple elements and array elements already were)

`base_expression_visitor::try_take_reference` (`ast/base_expression_visitor.cpp`) still only ever fires for a plain local variable/parameter — struct fields don't need it to, the same way tuple/array elements never did: `bootstrap.ann` gained `get` overloads keyed on `self: ~ reference(...) ref(of @is_struct)` (nested-concept structural pattern, matched against the *unwrapped* type by `pattern_matcher` — no changes needed to `is_struct_pattern.cpp`), delegating to `tuple_of(self)` — which now *is* reference-aware (`tuple_of_pattern.cpp`: `try_decompose_ref_of` first, relabel to `ref(of: TupleType)` at zero cost when the argument already was a reference) — and from there into the already fully ref-aware `tuple_get_pattern`. `ref(obj).field`, `obj.field` (implicit reference via a `ref(of: T)`-typed parameter), and plain `obj.field = value` assignment all work now — the last one through `base_expression_visitor::do_assign`'s uniform `ref(lhs)` + generic `set(self: ~ref(of $T), value)` path, with no struct-specific `set` needed at all (one was added mirroring `get` at first, then found to be dead code — nothing ever called its 3-argument shape — and deleted). The old native `struct_get_pattern`/`struct_set_pattern` (the latter had a confirmed multi-runtime-field write-loss bug, `STRUCT_FIELDS_PLAN.md`'s Part A.4) have since been **deleted entirely** too — once `ref(lhs)` started succeeding for every struct field case, nothing reachable from ordinary syntax (verified by disabling `do_assign`'s old direct-dispatch fallback and re-running the full test suite before removing it) could still reach them. See `STRUCT_FIELDS_PLAN.md` for the full history (verified current state, the design options considered, and the lessons paid for in wasted rounds), `IMPLEMENTATION_NOTES.md`'s `ref(T)` section for the `reference(EXPR)` conditional-reference mechanism, and `tests/test-suite/` for coverage.

## `ref(T)` item 3 — `functional_variable` (extern var) referenceability

Was recorded as an open question ("not established whether extending `try_take_reference` to this case is even sound, given a global's lifetime is different from a stack slot's"). It isn't actually open: a `functional_variable` only ever exists for an `extern var` declaration (`ast/declaration_visitor.cpp`'s `operator()(extern_var const&)`), and compiles down to a by-name ecall on each access — `semantic::push_variable`/`set_variable` become `extern_variable_get`/`extern_variable_set` (`vm/compiler_visitor.hpp`), looked up by the variable's name string, not a stack/frame index. There is no VM-managed `blob_result` behind it at all — the value lives entirely on the host side. `ref(T)` is, by construction, a `blob_reference` pointing at a real slot (`raw_reference_blob_result`/`reference_blob_result`, always `stack_at(index)` or a heap buffer — see `IMPLEMENTATION_NOTES.md`'s `ref(T)` section); there is nothing of that shape for an extern var to alias. So `try_take_reference` (which is keyed on a `variable_identifier varid` a `functional_variable` doesn't have at all — contrast `local_variable`, `semantic_fwd.hpp`) was never a wrong-but-fixable omission, and extending it here isn't sound at any lifetime policy — the gap isn't lifetime, it's that there's no address to begin with. Mirrors the pre-existing, symmetric rejection in `prepared_call.cpp`'s `deref()` ("cannot dereference functional variable"), which covers the assignment-target/`qname_reference_expression` path rather than the `ref(of: T)`-parameter path this item was about.

The one real gap this item did point at — that the failure, before this fix, was a generic, uninformative `cast_error` from `apply_cast`'s `implicit_cast` fallback rather than something naming the actual reason — is now fixed: `base_expression_visitor::operator()(fn_compiler_context::lookup_entity_result_t const&, qname const&)`'s `functional_variable` branch (`ast/base_expression_visitor.cpp`) now checks up front whether the calling context wants a reference (`wants_reference(expected_result.modifier)`, or `expected_result.type` decomposing via `try_decompose_ref_of`) and, if so, rejects immediately with an explicit `"cannot take a reference to an extern variable"` error instead of falling through to the generic cast path.

## `ref(T)` item 4 — nested references (`ref(of: ref(of: T))`)

`ref(of: ref(of: T))` is a legitimate, deliberately un-auto-collapsed construction: nothing about `rebind`'s existence or `get`/`set`'s generic shape requires collapsing more than one level of `ref` at a time, and — since `rebind` exists specifically to reach the *outer* slot — a language that allows one level of nesting to be meaningfully addressable at all should allow arbitrarily many. This design question was settled by reasoning alone; writing the test that was supposed to just confirm it then turned up a real, separate implementation bug in the primitives `get`/`set` compile down to — see `BUGFIXES.md`'s "`get()`/`set()` corrupted a genuinely nested `ref(of: ref(of: T))` instead of unwrapping exactly one level" entry for the bug and its fix (`annium_ref_get` and `smart_blob::operator=` in `invocation.hpp` both used to fully resolve through however many reference levels existed instead of stopping at exactly one, corrupting the middle level's type tag). The design conclusion itself needed no revision once the bug was fixed — the test now passes as originally intended:

- `get(self: ~ref(of $T))`/`set(self: ~ref(of $T), value: runtime $T)` (`bootstrap.ann`) already answer the "rebind vs. write through two levels" question on their own: `$T` captures whatever sits inside the outer `ref(of: ...)` exactly as it is, with no special-casing for `$T` itself being another `ref(of: U)`. So for `rr: ref(of: ref(of: i32))`, `set(self: rr, value: ...)` writes through **exactly one level** — it overwrites `rr`'s target slot with a brand-new `ref(of: i32)` value (silently repointing whatever `rr` pointed at, to a different `i32`), the same way `set` behaves for any other value type. It never writes through two levels to the innermost `i32` — reaching that takes an explicit second call (`set(self: get(self: rr), value: ...)`), chained by hand exactly the way `nt.0.0`-style tuple chains already work in `references.ann`.
- `deref_call_pattern`'s operator/function fallback (`functional/general/deref_call_pattern.cpp`) already only ever unwraps one level per retry too — confirmed by reading it: the retry is dispatched via `ctx.find`+`apply` directly, not through `base_expression_visitor`'s fallback-wrapping entry point, so a still-`ref`-typed result after one `get()` gets no second automatic pass. Auto-dereferencing an unbounded nesting depth was considered and rejected — only the first level is ever peeled off automatically, matching `set`/`get`'s own one-level-per-call behavior above.
- `rebind` reaches the **outer** slot (the `ref(of: ref(of: T))` variable's own storage); `get`/`set` reach exactly **one level in** (the `ref(of: T)` value that outer slot currently holds). Nothing ever auto-collapses two levels at once, in either direction — symmetric and requires no special-casing anywhere in the existing mechanism.

Tested in `references.ann`'s "nested references" section (`read_through_nested`/`write_through_nested`/`repoint_via_set`), including confirmation that `try_take_reference`'s path (a) (`base_expression_visitor.cpp`) is what lets a `ref(of: T)`-typed variable be implicitly coerced one level deeper into a `ref(of: ref(of: T))`-declared parameter in the first place — see `IMPLEMENTATION_NOTES.md`'s `ref(T)` section, "Nested references (`ref(of: ref(of: T))`) are real, deliberately not auto-collapsed, and reached only through path (a)," for the mechanism. The `smart_blob::operator=`'s write-through branch (`invocation.hpp`, `is_ref(rhs->type)` case) that motivated this entry *was* the bug, not just untested code — see `BUGFIXES.md`.

Surfaced in a design-review conversation immediately after `ref(T)` v1 shipped; resolved in a later design-review conversation without needing a design change, only a test — which is what then surfaced the unrelated implementation bug above.

## A `match`/`switch` construct to narrow a `union`-typed value back down to its active case

Was tracked in `FUTURE_WORK.md` as deliberately deferred design work (structural enums shipped construction/casting *into* a union with no way back out). Implemented as a `match` expression (`scrutinee { pattern => expr, pattern { block }, ... }`) desugaring entirely to the pre-existing `apply(to:, visitor:)` union-dispatch builtin — no new runtime dispatch mechanism was needed, since `apply` already provided native `which`-tag switching, per-arm result-type unification, casting into an already-known expected type, and exhaustiveness as an emergent property of overload resolution against every union member. See `IMPLEMENTATION_NOTES.md`'s "`match` expression" section for the full mechanism (grammar, short enum-local case names, the bare-case value-pattern rewrite, the `constexpr_not_a_typename_value`-vs-type modifier bug found and fixed along the way) and `ANNIUM_SYNTAX.md`'s "`match`" section for the surface syntax. Confirmed stable by the full test suite, including `tests/test-suite/match_expression.ann`.

One related item is still open and remains tracked separately in `FUTURE_WORK.md`: `EnumName.CaseName(args)` (dotted *structural*-case construction, as opposed to the already-working bare-case `EnumName.CaseName`). The other originally-listed gap here — destructuring a struct's own named fields directly in a pattern — turned out not to be a gap at all; see the next entry for the corrected understanding and the actual fix, scoped to `match` specifically.

## Field-destructuring `match` arms (`Leaf(name $n, value $v) => ...`) — not a `pattern_matcher`/`struct_entity` bug, fixed as `match`-specific sugar instead

Was first misdiagnosed as a `pattern_matcher::do_match`/`struct_entity` bug (`FUTURE_WORK.md`'s "Structural pattern destructuring of a struct's own named fields doesn't work"): `do_match` matches a pattern's named/positional subfields against `ent_type.signature()->fields()`, and `struct_entity`'s own signature never carries any field descriptors for a plain `struct Name => (fields)` — so a struct pattern naming a subfield (`~Tree::Leaf(name $n)`) always failed with "Cannot match named field in signature". A first fix attempt redirected `do_match` to the struct's *underlying tuple* signature (which does have real field descriptors) whenever the struct's own signature was empty — landed, tested, then reverted after a closer look at `struct_fn_pattern` (a **parameterized** struct's constructor pattern, e.g. `iterator(=array(...))`) made clear the premise was wrong: a struct's own signature isn't "not yet filled in with its runtime fields" — it deliberately describes the type's *constructor/selector* shape (empty for a plain struct, since there's nothing to select between; the constructor's own parameters for a parameterized one, which is exactly what `struct_fn_pattern::apply()` already populates `sig_` with, directly from the matched constructor call). Redirecting to the underlying tuple was conflating that with the *instance's* runtime field layout — a different concept — and the `do_match` fix's own gating (needed to stop it from breaking `iterator(=array(...))`, which legitimately needs the *constructor's* signature, not the tuple's) was itself a symptom of that conflation. **`pattern_matcher.cpp`'s `do_match` was reverted to its original, pre-fix form** — a struct pattern with named fields fails to match a plain struct's own signature again, correctly, since a plain struct genuinely has no constructor-selector fields to match against.

**The actual, correct place for `Leaf(name $n, value $v)`-style destructuring is `match`'s own arm-rewriting**, not general structural pattern matching: `base_expression_visitor::operator()(match_expression const&)` (`ast/base_expression_visitor.cpp`) now recognizes an arm pattern with a non-empty field list and rewrites the *arm itself* rather than trying to make it match structurally — the actual matched pattern is stripped down to a bare type check (`~Leaf`), and one `let $n = $0.name;` per bound field is synthesized and prepended to the arm's own body, reusing the already-correct, generic `get(self:, property:)`/`tuple_of` field-access machinery exactly as if the caller had written `$0.name` by hand. This is a strict improvement over the abandoned `do_match` approach: `$n` is now the field's actual runtime *value* (previously, even with the reverted fix, a field-bound pattern variable only ever gave the field's declared *type* — the "deliberately not fully solved" gap the first attempt left open no longer applies, since this path never goes through `pattern_matcher`'s binding mechanism at all).

**A real lifetime subtlety, worth remembering for any future AST-synthesis-during-compile site:** the rewritten arm *body* (unlike the arm-pattern rewrites `match` already did for short-name resolution, which only need to survive the synchronous `apply(...)` matching call within the same function) becomes the eventual `internal_function_entity`'s `body_`, consumed lazily — possibly well after `operator()(match_expression const&)` returns — so a locally-scoped `std::deque`/`arena` would leave it dangling. Fixed by using `environment::acquire_arena()`/`release_arena()` (the same pool `parser_context` itself draws from) for just the synthesized nodes that need it — verified safe by reading `entity_registry`/`arena`'s actual mechanics: `release_arena` returns the arena to a reuse pool without ever calling `clear()`/`release()` on it, so previously-allocated blocks are never freed or overwritten; durable for as long as `environment` itself lives, not just for this one call.

See `IMPLEMENTATION_NOTES.md`'s "match expression" section for the full mechanism and `tests/test-suite/match_expression.ann` for coverage (named-field destructuring in both arrow and block arms, and a partial destructure that names only one of two fields).

## `struct_decl`/`enum_decl` moved onto `forward_declaration_visitor`, and eager field-signature validation for both

Prompted by the struct-pattern-destructuring fix above (`declaration_visitor.cpp`'s two-pass split — `forward_declaration_visitor` then `declaration_visitor`, see `annium_impl::annium_impl()` in `annium.cpp` — already existed for `fn_decl`, but `struct_decl`/`enum_decl` were both handled entirely in the second pass).

**`struct_decl` moved first**, mirroring `fn_decl` exactly: both branches (a plain `struct_entity` shell, and a parameterized struct's `struct_fn_pattern`) now register during `forward_declaration_visitor::operator()(struct_decl const&)`; `declaration_visitor`'s own handler was left a no-op at that point — a struct's own identity is now available file-order-independently across the translation unit, while field/parameter resolution stays exactly as lazy as it already was.

**`enum_decl` moved next** — initially thought to need a harder redesign (a placeholder identity for the enum's own qname, since a `union(...)` can only be built *after* every case's own id is known), but that turned out unnecessary: a `struct_entity`'s own id and `get_type()` (which `make_union_type_entity`'s const-vs-type-per-element decision reads) are both already valid the instant the entity is *constructed*, well before `struct_entity::build()` ever runs — so collecting each case's id and building the union is shell-only work too, exactly like `struct_decl`'s own registration. The *entire* previous `enum_decl` handler body moved to `forward_declaration_visitor::operator()(enum_decl const&)` unchanged.

**With every top-level struct/enum's shell now guaranteed to exist before `declaration_visitor`'s second pass touches any of them, eager field validation became safe to add** — closing the forward-reference hazard (a struct/case referencing another type declared later in the same file) that made it unsafe to eagerly build fields directly inside the single old pass. `declaration_visitor::operator()(enum_decl const&)` was repurposed (not left as a no-op) to walk each structural case and force-build its field signature via `underlying_tuple_eid(ctx)`, propagating any error right there at the enum's own declaration site — instead of leaving it to whenever (if ever) something first demanded the build. `declaration_visitor::operator()(struct_decl const&)` got the same treatment for the plain (non-parameterized) case; a parameterized struct is deliberately left alone here, since it has no single "the" instantiation to validate — only concrete calls to it do, each with its own argument-dependent field types.

See `IMPLEMENTATION_NOTES.md`'s "Function declarations & call dispatch" section for the full mechanism.
