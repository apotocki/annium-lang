# Implementation Notes

Deep-dive remarks on how specific subsystems of the Annium compiler are *intended* to work, gathered while implementing features — not a spec, not exhaustive. Referenced from `CLAUDE.md`. Add to this file (don't inline it back into `CLAUDE.md`) whenever a task turns up a non-obvious mechanism or a "don't do X, it was tried and reverted" lesson. For an actual bug found and fixed (something that was *wrong*, not just non-obvious), log it in `BUGFIXES.md` instead.

## Stale / dead code caveat

Several places in this codebase reference APIs that no longer exist (e.g. `environment::get_builtin_function`, `qnregistry()`) or sit inside `#if 0` blocks — this is a mid-refactor codebase, not a fully-compiling reference. A grep hit is not proof a code path currently compiles; check whether it's guarded by `#if 0`/`#if` or lives in a file actually listed in the build (see "Adding a new source file" below) before treating it as a working example.

## Adding a new source file

A new `.cpp`/`.hpp` pair must be registered in **three** places or one build will silently miss it: `projects/cmake/annium/CMakeLists.txt` (`LIBRARY_SOURCES`, `.cpp` only), `projects/vs/annium/annium.vcxproj` (`ClCompile` + `ClInclude`), and `projects/vs/annium/annium.vcxproj.filters` (same, plus a `<Filter>` tag for IDE grouping).

## Function declarations & call dispatch

Every kind of callable (regular `fn`, struct constructor, `extern fn`, compiler builtins) is compiled through the same two-stage pipeline:

1. **Declaration time** (`ast/declaration_visitor.cpp`): a `fn_pure`/`fn_decl` AST node becomes a `functional::pattern` subclass (`functional/*.hpp`), registered on a `functional` object via `functional::push(pattern)` or `set_default_entity(...)`. `basic_fn_pattern` (`functional/basic_fn_pattern.*`) parses the parameter list and result expression/pattern and implements the generic `try_match`/parameter-matching machinery; concrete patterns derive from it:
   - `internal_fn_pattern` — a body-defined `fn`; lazily builds an `internal_function_entity` (inlinable).
   - `builtin_fn_pattern` (renamed from `external_fn_pattern`) — a fixed, C++-compile-time-known efn table entry (numeric `extfnid`), used for compiler builtins and `__extern_invoke` itself (registered via `environment::set_builtin_extern`). Entity is `builtin_function_entity` (renamed from `external_function_entity`).
   - `extern_fn_pattern` — a natively declared `extern fn name(...);`. Has **no entity of its own** — see below, it just synthesizes a call to the same builtin `__extern_invoke` uses.
   - `struct_fn_pattern`, `typefn_pattern` — struct-with-parameters constructors, type-level functions.
2. **Call codegen**: every call ultimately becomes a `semantic::invoke_function{entity_identifier}` semantic expression. The **single** dispatch point is `compiler_visitor_base::operator()(semantic::invoke_function const&)` in `vm/compiler_visitor.hpp` — it `dynamic_cast`s the resolved `entity` to decide how to emit code (`internal_function_entity` → `append_call`/inline expansion, `builtin_function_entity` → `append_ecall(extfnid)`). **Adding a new callable kind that needs its own codegen means adding both a new entity subclass and a new branch here** — but check first whether it can instead be expressed as a synthesized call to an *existing* builtin (see `extern_fn_pattern` below); that avoids touching this dispatcher at all.

### `extern fn` is sugar for a synthesized `__extern_invoke` call — no dedicated entity/codegen branch

`extern fn name(runtime T...) [-> R];` does **not** get its own entity or VM opcode. `extern_fn_pattern::apply()` (`functional/extern_fn_pattern.cpp`) just emits the same semantic expressions a hand-written `__extern_invoke(name, args..., argcount)` call would produce: push the fully-qualified name as a runtime string constant, push every argument (guaranteed non-const — see below), push the trailing `u32` arg count, then `invoke_function` targeting whichever of `builtin_eid::extern_invoke` / `builtin_eid::extern_invoke_void` matches whether the declared result is void — both are just the existing `builtin_function_entity` for `annium_invoke`/`annium_invoke_void` (`library/annium_library.cpp`), the same C++ functions backing `__extern_invoke` itself, now additionally captured into `builtin_eids_` (`environment::builtin_eid`) at registration time in `annium_environment.cpp` so they can be looked up directly instead of only reachable via `__extern_invoke`'s own call-matching. This means codegen for `extern fn` is just the ordinary `builtin_function_entity` → `append_ecall(extfnid)` path — no `dynamic_cast` branch, no custom stack convention to get right. (An earlier version of this feature introduced a dedicated `extern_function_entity` and a bespoke `vm::context::extern_function_call` stack convention with its own reserved-slot/pop-count bookkeeping; that turned out to be unnecessary complexity duplicating what `__extern_invoke` already does; it was removed. `vm::context::extern_function_call` still exists in `vm/annium_vm.cpp` but is unused again — don't resurrect it for this without a good reason.)

The function's runtime lookup name is every part of its qname joined with C++ `::` (no leading `::`), not just the leaf identifier — see `join_qualified_name` in `extern_fn_pattern.cpp`. A function declared inside `namespace foo` as `extern fn bar(...)` is looked up as `"foo::bar"`; a top-level one as `"bar"`.

`extern fn` parameters must be declared `runtime` explicitly (e.g. `extern fn iv_call(runtime integer);`); `declaration_visitor::operator()(fn_pure const&)` rejects any parameter whose modifier isn't `can_be_only_runtime` with a `basic_general_error`. This isn't cosmetic: `basic_fn_pattern::apply_arguments`/the matcher skip pushing any argument matched as constexpr, and `extern_fn_pattern::apply()` asserts every matched argument is non-const before pushing it — a parameter that's merely *allowed* to be constexpr (the default `constexpr_or_runtime_type` modifier) could resolve as constexpr for some call sites (e.g. a literal argument) and not others, and the receiving `annium_invoke`/`annium_invoke_void` has no way to know an argument was silently omitted. Don't try to fix this by silently forcing the modifier to `runtime_type` in `declaration_visitor` instead of rejecting — that was the first approach here and it's surprising/magic from the caller's point of view for no good reason.

When synthesizing AST nodes that aren't in the parsed source (e.g. `EXTERN FN fn-decl` in `annium.y` defaulting an unspecified result to void), prefer doing it in the **grammar action** via `ctx.make<T>(...)` (the `parser_context`'s arena, which lives for the whole parse of that resource) rather than later in `declaration_visitor`. If you do need to allocate from a later pass, use a short-lived local `arena` (`ast/arena.hpp`) that stays in scope for as long as anything might read the pointer — `arena`'s destructor frees all of its blocks, so a pointer surviving past the `arena` going out of scope is a dangling pointer (see `environment::parse_extern_fn` for that pattern: allocate and consume within the same function body).

## VM instruction dispatch (`vm2.hpp`) is code-generated from `op`'s `VMOP_*` annotations

`sonia/utility/lang/vm.hpp` is now a thin forwarding shim (`#if 1` / `#include "vm2.hpp"` / `#else` the old hand-written implementation, permanently excluded); `vm2.hpp` is the real, live implementation. `virtual_stack_machine<ContextT>::traverse()` (the bytecode interpreter loop) is not hand-written any more — it's generated by a private, external tool (`sonia-pygen`, not vendored into this repo) from annotations on the `op` enum, which was hoisted out of `virtual_stack_machine<ContextT>` to namespace (`sonia::vm`) scope specifically so an external AST-based tool can see and annotate it (it never depended on `ContextT` in the first place).

**Annotation grammar** (`vmop_proto.hpp`): each `op` enumerator carries exactly one of four tag combinations, via `[[clang::annotate(...)]]`-backed macros (inert/no-op unless `__has_cpp_attribute(clang::annotate)`, i.e. only meaningful to the generator tool's Clang-based parse, never to MSVC/GCC compiling the real project):
- `VMOP_SIMPLE` — no operand, doesn't redirect control flow (e.g. `noop`, `pop`, `dup`).
- `VMOP_ARG` — reads one varint operand before dispatch (e.g. `push`, `set`).
- `VMOP_JUMP` — the handler's return value replaces `address` instead of it auto-advancing (e.g. `callp`). Combines with `VMOP_ARG` for the jump-instruction family (`jmp`/`jg`/`jge`/.../`jnen` — all 21 variants have `VMOP_ARG VMOP_JUMP`, since deciding *where* to jump needs an operand).
- `VMOP_CUSTOM` — excluded from generation entirely; `call`/`ecall`/`ret` are the only three (irregular arg count, packed short-form encoding, and early-`return`-from-the-interpreter-loop respectively don't fit the uniform shapes above).

No tag at all, or a tag combination outside the four above, is a hard generation-time error (not a silent default) — see `BUGFIXES.md`'s `op::ecall`/`environment::compile` entries for what silently-wrong VM dispatch decoding looks like in practice; the strictness here exists specifically to make adding a new opcode without deciding its shape a build failure instead of a runtime miscompile.

**Generated output** (`vm2.gen.hpp`, checked in): one file, containing *both* dispatch forms behind `#if defined(__GNUC__) || defined(__clang__)` — a switch-based form (what MSVC gets, since it defines neither macro) and a computed-goto (label-as-value) form for GCC/Clang. `call`/`ecall`/`ret` (the `VMOP_CUSTOM` three) are spliced in via hook macros `vm2.hpp` `#define`s immediately before `#include "vm2.gen.hpp"` and `#undef`s immediately after: `SONIA_VM_GEN_CUSTOM_<NAME>_SWITCH` / `SONIA_VM_GEN_CUSTOM_<NAME>_GOTO`, one pair per custom opcode. The packed `ecall` short form (`op_byte >= 128` encodes the callee index directly in the byte, no separate operand) is hardcoded in the generator's template, not derived from per-value data — it assumes an opcode literally named `ecall` exists and is `VMOP_CUSTOM`.

**The computed-goto form has no per-dispatch bounds check**, unlike the switch form's `while (address < code_.size())`. It relies on every reachable instruction sequence ending in a control-flow op that redirects `address` somewhere valid — `op::ret` included. That invariant did not hold before this session (`environment::compile` never appended a trailing `ret` for a function body without an explicit `return` — see `BUGFIXES.md`); it had to be fixed first, since without it the goto form would read `code_[address]` past a function's real end and jump to a garbage label address.

**GCC vs. Clang extension mismatch, found the hard way:** the dispatch table was originally generated using GNU C designated array initializers (`[0 ... 255] = &&L_bad_op`) — Clang accepts these in C++ as a portability extension, **GCC does not** (it parses `[0 ... 255]` as a lambda capture-list and fails with "expected identifier before numeric constant"). Fixed by generating a plain *positional* 256-entry array (`{ &&L_noop, &&L_jmp, ..., &&L_bad_op, ..., &&L_ecall_packed, ... }`) instead — needs nothing beyond label-as-value itself, which both compilers accept identically. Don't reach for designated initializers in anything meant to compile on both toolchains without checking GCC specifically first; Clang being permissive is not evidence something is portable.

Label-as-value/computed-goto themselves are still non-standard and trip `-Wpedantic` (once per `&&label`, i.e. 256 times over the dispatch table) — the generated `traverse()` for the goto form is wrapped in `#pragma GCC diagnostic push` / `ignored "-Wpedantic"` / `pop` (both GCC and Clang understand the `#pragma GCC diagnostic` spelling), scoped to just that function so `-Wpedantic` stays fully active for the rest of the codebase.

**Build wiring:** `projects/vs/annium/annium.vcxproj` has a `CustomBuild` step on `vm2.hpp` that invokes `sonia-pygen`'s `main.py`, gated on `'$(PythonGenPath)' != ''`. `PythonExePath`/`PythonGenPath` are only ever set in `Directory.Build.local.props` (gitignored — `sonia-pygen` is a private tool, this is a public repo) pointing at a local clone; without them the step is skipped and the checked-in `vm2.gen.hpp` just compiles as-is. `pygen.json` (repo root) is the generator's config (include dirs, `SONIA_DO_NOT_INCLUDE_GEN` so the generator's own Clang-based parse of `vm2.hpp` doesn't try to `#include` a possibly-stale/missing `vm2.gen.hpp` while extracting the `op` enum's annotations). The CMake/GCC side has no codegen step at all — it only ever compiles whatever `vm2.gen.hpp` is checked in.

**Adding a new opcode:** give it exactly one `VMOP_*` tag combination in `vm2.hpp`'s `op` enum. If it fits one of the four regular shapes (`VMOP_SIMPLE`/`VMOP_ARG`/`VMOP_JUMP`/`VMOP_ARG VMOP_JUMP`), both dispatch forms are generated automatically on the next `sonia-pygen` run — no hand-written dispatch code needed. If irregular, tag it `VMOP_CUSTOM` and hand-write both `SONIA_VM_GEN_CUSTOM_<NAME>_SWITCH` and `SONIA_VM_GEN_CUSTOM_<NAME>_GOTO` in `vm2.hpp`.

**Unrelated dead code this surfaced:** `append_jt`/`append_jtx`/`append_jf`/`append_jfx` referenced `op::jt`/`jtp`/`jtn`/`jf`/`jfp`/`jfn`, which are commented out of the enum and never had a dispatch case. MSVC tolerated the dangling references (it doesn't eagerly check non-dependent names in an uninstantiated class template's member bodies); Clang, used by `sonia-pygen`'s AST parse of `vm2.hpp`, does and failed outright. See `BUGFIXES.md` — commented out in `vm2.hpp`; `vm.hpp`'s dead `#else` branch still has the original, unfixed versions, but nothing compiles that branch any more.

## Error-tree printing prints leaf-first, longest chain first (`errors.hpp`/`annium_errors.cpp`)

An `error` (`errors.hpp`) is a tree, not a flat message: any node can carry a single `cause()` link (an "AND" step — "this happened because of that"), and `alt_error::alternatives` is a list of mutually-exclusive candidate failures (an "OR" branch — e.g. one entry per overload candidate that failed to match a call, built in `functional::find`, `functional/functional.cpp`). The actual failure reason a user cares about is almost always a leaf deep in one of these branches (a `type_mismatch_error` from `functional/parameter_matcher.cpp`/`pattern_matcher.cpp` rejecting one candidate's parameter), not the root (`can't match the function call`).

`error_printer_visitor::print(error const&)` (the single entry point — `environment::print_to(ostream&, error const&)` calls it, and it's what `error::rethrow` ultimately goes through via `environment::print<error>`) does not print the tree top-down. It first calls the anonymous-namespace `collect_chains()` in `annium_errors.cpp`, which walks the tree and returns every root-to-leaf chain: `alt_error` nodes are transparent — they contribute no printed line of their own, they just fan the walk out into one chain per alternative — while every other node follows its single `cause()` link. The resulting chains are `std::stable_sort`ed longest-first (the deepest chain is treated as the most specific, and so most likely relevant, explanation — a heuristic, not a proof; a shallow alternative can occasionally be the real intended overload while a long chain is a generic combinator failing for unrelated reasons deep inside) and printed via `print_chain()` **leaf-to-root** (reverse of the chain's natural root-to-leaf order), joined by `"required by:"`. Only the first `max_printed_chains` (currently 3) chains are printed in full; the rest are collapsed into a single `"... and N more similar candidate(s) not shown"` line, so a call with many rejected overload candidates doesn't dump every one of them.

Each `operator()(general_error const&)`/`operator()(binary_relation_error const&)`/etc. override renders **only that one node** (location/object/description) — none of them recurse into `cause()` any more; the chain-walking in `print()`/`print_chain()` is the only place recursion happens. `operator()(alt_error const&)` is dead code in the normal flow (an `alt_error` is always consumed by `collect_chains()` before any node gets `visit()`ed) but is kept as a correct fallback — it now calls `print()` per alternative (full leaf-first sub-tree) instead of the old flat `visit()`, in case something ever visits an `alt_error` directly. `circular_dependency_error` (a fixed, ordered list of `circle_items` describing one real dependency cycle — not alternatives) stays atomic/self-contained by design and is not expanded by `collect_chains()`; its `operator()` prints each item via `print()` too, so a chain nested inside one cycle link still gets the same leaf-first treatment, indented one level under the `"circular dependency error:"` header.

`function_call_match_error::description()` still has an unused code path that would embed a sub-error's *rendered text* directly into its own description string via `e.print(*reason_)`, bypassing `cause()`/`collect_chains()` entirely — harmless today only because every call site constructs it with a null `reason_` (`functional.cpp`'s `functional::find`, the one active construction site, always passes `nullptr`; the line that would populate it with a `reason_` is commented out). If `function_call_match_error` ever gets a real `reason_` again, prefer wiring it through `set_cause()` instead of the description-string embedding, so it participates in chain collection/ordering like everything else.

## Compile-time `@concept` predicates (parameter matching)

`@name` on a parameter pattern (see `ANNIUM_SYNTAX.md` for the surface syntax) is a compile-time constraint: it requires a registered callable `fn name(t: typename) -> bool` and treats the parameter as matching only when calling that predicate with the candidate's type returns `true`. This was **inert until fixed** (see below) — worth knowing if you find `@X` somewhere and it doesn't seem to constrain anything; check `pattern_matcher.cpp`'s git history / this note before assuming it's dead syntax.

**Mechanism** (`functional/pattern_matcher.cpp`, `do_match_concepts`): for each `@name` in `syntax_pattern.concepts`, resolve the qname via `fn_compiler_context::lookup_qname`, synthesize a single-argument call via `call_builder` whose argument is a `syntax_expression` wrapping the candidate's `entity_identifier` directly (`entity_identifier` is itself a `syntax_expression` variant alternative — `base_expression_visitor::operator()(entity_identifier const&)` evaluates it back to that exact entity as a constexpr value, which is what makes this "pass an already-resolved value into a fresh synthetic call" trick work without needing real source syntax), dispatch it through `fn_compiler_context::find(qname_identifier, ...)` (the general by-qname-id call path, not the `builtin_qnid`-only convenience overload), and require the constexpr result to equal `true_`. All concepts on a pattern are ANDed (first failure short-circuits). On failure, returns `concept_not_satisfied_error` (`errors/concept_not_satisfied_error.*`).

**Existing predicates implementing this contract**: `is_struct` (`entities/struct/is_struct_pattern.*`), `tuple_of` (same dir, returns the tuple type rather than bool), `numeric` (`entities/literals/numeric_pattern.*`, added for the `__to_i8`.../`__to_u64` builtins' `runtime @numeric` parameters — see `library/annium_library.cpp` / `annium_environment.cpp`). All are registered under a `// TRAITS/CONCEPTS` comment block in `annium_environment.cpp`.

**Watch out:** the candidate type passed to a predicate can itself be `typename` (not a concrete type) when a bare/unconstrained placeholder parameter carries a concept and gets called with an actual *type* as the argument (rather than an instance) — `typename_`'s own `get_type()` is empty/invalid, since there's no "type of typename" in this system. `is_struct_pattern` used to crash on this; see `BUGFIXES.md` for the fix and the shape to prefer in new predicates.

## `annium_numeric_to_*` / `__to_iN` numeric casts

`library/annium_library.cpp`'s `annium_numeric_to_i8/ui8/i16/.../ui64` (registered as `__to_i8`.../`__to_u64` in `annium_environment.cpp`) implement `static_cast`-style truncating conversion from *any* numeric `blob_result` (fixed-width int, bigint, float16/32/64, decimal) to a specific fixed-width integer type. The truncation itself needs no bespoke bit-twiddling: `numetron::basic_integer_view<uint64_t>::operator T()` and `numetron::basic_decimal_view<uint64_t>::operator T()` (in `modules/numetron`) already implement exactly "truncate to T's width, wrap on overflow" for arbitrary-magnitude sources — the whole family reduces to dispatching on `is_floating_point(blob_type)` to pick `decimal_view` vs `integer_view`, then `static_cast<T>`. Compile-time argument validation is done via the `@numeric` concept (see above) on each builtin's signature; the C++ implementation itself doesn't need to re-validate the argument's type.

`annium_numeric_to_f16/f32/f64/decimal` (`__to_f16`/`__to_f32`/`__to_f64`/`__to_decimal`) round out the family for non-integer targets, and are simpler than the fixed-width ones: `numetron::decimal_view` already represents *any* numeric source exactly (its own `from_blob` dispatch handles fixed-width int, bigint, f16/f32/f64, and decimal sources alike — see `sonia::invocation`), so these never need the `is_floating_point(blob_type)` branch the integer family uses to pick between `integer_view`/`decimal_view` — always go through `arg.as<numetron::decimal_view>()`, then `static_cast<float/double>` (f32/f64), `numetron::float16_cast(...)` (f16 — `float16` isn't a `std::floating_point` type so it can't use the `operator T()` `static_cast` path, needs the dedicated free function), or `decimal_blob_result(...)` directly (decimal).

**`numeric_cast` — user-facing wrapper, split across two independent registrations of the *same qname*.** `bootstrap.ann` declares plain `.ann` overloads (`inline fn numeric_cast(runtime @numeric) ~> i8 => __to_i8($0);` etc., one per target) that only match a *runtime* argument — covering all 12 targets (`i8/u8/i16/u16/i32/u32/i64/u64/integer/f16/f32/f64/decimal`). `entities/literals/numeric_cast_constexpr_pattern.*` is a separate, hand-written C++ `functional::pattern` registered for the identical qname (`fregistry_resolve(qname{ make_identifier("numeric_cast"sv) })` in `annium_environment.cpp`, *not* a `builtin_qnid` — plain string-qname resolution) that instead requires a *constexpr* argument and folds the same conversion at compile time via `env.make_generic_entity(...)`, reusing `numeric_literal_implicit_cast_pattern`'s established "read a `generic_literal_entity`'s stored `smart_blob` via `.as<numetron::integer_view/decimal_view>()`, construct a new one via `env.make_generic_entity`" shape — but, unlike that pattern, never rejects on precision loss (`numeric_literal_implicit_cast_pattern` is a *checked* conversion, architecturally the wrong fit here). Mirrors the runtime side's split: the 8 fixed-width integer targets bit-truncate (`numeric_cast_truncate<T>`); `integer`/`f16`/`f32`/`f64`/`decimal` don't need that and go through the same `decimal_view`-for-everything path as their runtime counterparts.

(`annium_to_integer`, the C++ function `~> integer` calls into, used to throw for every fixed-width integer/boolean source — see `BUGFIXES.md` if you hit conversion errors there that look wrong.)

Mixing a C++-registered pattern into an otherwise `.ann`-declared name's overload set is safe and already how the codebase works generally: `functional::push`/`find` (`functional/functional.cpp`) don't distinguish pattern origin, only `weight` (tier) and then `penalty` (within a tier) — and every registration path (`.ann` `fn`, `extern fn`, C++ builtin) funnels through the same `environment::fregistry_resolve(qname)` to get-or-create the same `functional` object for a given qname, regardless of registration order.

**Disambiguating the constexpr vs. runtime overload for a literal argument happens via `match_penalty`, not `weight`.** Both `numeric_cast` overload families are structurally viable for a literal argument like `numeric_cast(300)` (a `runtime` parameter happily accepts a constexpr-capable value by materializing it). `base_expression_visitor::apply_cast` (`ast/base_expression_visitor.cpp:76-107`) flags `has_been_casted = true` whenever a constexpr value has to be pushed through `implicit_cast` to satisfy an incompatible modifier (e.g. a `runtime`-only parameter) — the general "implicit conversion should cost something" signal, reaching `prepared_call.cpp`'s `argument_descriptor_t::has_been_casted` and then `parameter_matcher.cpp`'s `constraint_matcher`, which folds it into `match_penalty.casts` (compared first, before `placeholders`/`variadics`/`cast_capable_matches`, by `match_penalty::operator<=>`, `functional/match_penalty.cpp:19-38`) for both the plain type-expression and the `@concept`/pattern branch alike. `numeric_cast_constexpr_pattern` stays at the default weight — no per-pattern weight override needed, `casts` alone (`0` for the constexpr match vs `1` for the materializing runtime match) is decisive. (Getting the pattern branch's accounting right, and a related field rename, took a wrong turn first — see `BUGFIXES.md`.) This is a general mechanism — any future ambiguity between a "this argument already has exactly the right constness" overload and a "this argument needs materializing" overload resolves itself the same way, for any `@concept`-constrained parameter.

**By design, `let x: T = <constexpr-computable-expr>;` does not force `x` to become a runtime value.** Values become runtime only when explicitly required (e.g. `runtime_cast(x)`, `functional/general/runtime_cast_pattern.cpp` — requests the argument with a hard `value_modifier_t::runtime_value` and asserts `!is_const_result` in `apply()`) or when they come from something that itself produces a runtime value. A plain `let` binding stays constexpr-foldable, so referencing it later can still resolve as a compile-time constant, e.g. against a `constexpr`-only parameter. **Test-writing consequence**: a plain `let`-bound argument proves nothing about runtime-only argument handling — use `runtime_cast(...)` when a test needs to force that. This tripped up the first draft of both `match_priority.ann`'s `tesnfn4` test and several `numeric_cast(...)` calls in `casts.ann` (fixed to use `runtime_cast(...)` where the runtime `.ann` overload, not the constexpr pattern, was the thing meant to be under test).

## Generic numeric arithmetic (`__plus`/`__minus`/`__multiply`/`__divide` / `numeric_promotion.hpp`)

`a + b` between two numeric types (any pair of `i8/u8/.../u64/f16/f32/f64/integer/decimal`, `bool` excluded — it's a cast source, not an arithmetic operand) no longer needs an explicit `numeric_cast`. This mirrors `numeric_literal_unary_minus_pattern`'s shape (**not** `numeric_cast`'s two-separate-registrations-under-the-same-qname shape): a single custom `functional::pattern`, `numeric_literal_plus_pattern`, is the *only* thing registered under `builtin_qnid::plus`'s qname (`plus_fnl.push(make_shared<numeric_literal_plus_pattern>())` in `annium_environment.cpp`, right next to the existing `minus_fnl.push(make_shared<numeric_literal_unary_minus_pattern>())`) — it handles constexpr folding itself and, for anything involving a runtime operand, hardcodes a call to a separate, privately-named generic runtime extern (`__plus_numeric(runtime, runtime)`, `builtin_eid::add_numeric`, `annium_operator_plus_numeric` in `library/annium_library.cpp`) rather than exposing any typed overload directly under `__plus`. This is why the old `__plus(runtime integer, runtime integer)~>integer` / `__plus(runtime decimal, runtime decimal)~>decimal` typed registrations and their one-C++-function-per-type-pair implementations (`annium_operator_plus_integer`/`_decimal`) are gone — a single type-erased runtime extern (using `numeric_builtin_eid_of`/`blob_type` dispatch, no `blob_type_selector` template fan-out) replaces them for every pair.

**The result type is the "strongest" of the two operand types** — `strongest_numeric_type(builtin_eid, builtin_eid)` in `entities/literals/numeric_promotion.hpp`. It's a *join* over the existing `is_always_safe_runtime_conversion` directed safe-conversion graph (the same table `numeric_literal_implicit_cast_pattern` already used for single-argument implicit casts) rather than a new hand-authored promotion table: the result is the smallest type both operands safely convert into. Same-family operands pick the wider/dominant one (`i8+i32 -> i32`, since `i8` already safely reaches `i32`); operands incomparable in that graph (signed/unsigned collisions, mixed int/float, `integer` vs `decimal`) escalate to the smallest common safe supertype (`i32+u32 -> i64`, `i64+u64 -> integer`, `i32+f32 -> f64`, `integer+decimal -> decimal`).

**Watch out:** naively joining two integral-kind types over the *full* 13-type graph is ambiguous in general — e.g. `i8+u8` can safely reach both `i16` and `f16` (an `i8`/`u8` value trivially fits either), and neither dominates the other in that reduced candidate set, so there's no unique bottom element. `strongest_numeric_type` special-cases this: when *both* operands are integral-kind (`i8..u64`/`integer`), floating-kind candidates (`f16/f32/f64`) are excluded from the candidate set before finding the bottom element, so two integers never join to a float just because some narrow float also happens to fit. Mixed integral/floating inputs don't need this exclusion (a floating operand's own safe-list never contains an integral target, so no equivalent ambiguity arises there).

**A literal operand paired with a runtime operand does *not* just use `strongest_numeric_type` directly** — bare numeric literals default to type `integer` (arbitrary precision; see `numeric_cast`'s bootstrap notes above), and `strongest_numeric_type(i8, integer)` is unconditionally `integer` regardless of the literal's actual value, which would make *every* `runtime_i8_var + 1` expression allocate a bigint. Instead, `widen_for_literal_fit` (`numeric_promotion.hpp`) walks the runtime operand's own type's safe-conversion targets (smallest first) and returns the first one the literal's actual *value* fits (reusing `can_convert_constexpr_value_safely`, the same value-fit check `numeric_literal_implicit_cast_pattern` uses) — so `i8_var + 5` stays `i8`, and only `i8_var + 1000` (which doesn't fit `i8`) widens, and only as far as `i16`, not all the way to `integer`. The runtime `__plus_numeric` extern doesn't need to know any of this: it independently recomputes `strongest_numeric_type` from the two operands' *actual* runtime blob types every time it runs, and by construction `strongest_numeric_type(runtime_type, widened_type) == widened_type`, so materializing the literal at the widened type (not its default `integer`) is sufficient — no separate runtime-side cast of the other operand is ever emitted.

**`__minus` (`a - b`) mirrors `__plus` exactly** (`numeric_literal_minus_pattern`, `annium_operator_minus_numeric`/`builtin_eid::subtract_numeric`/`__minus_numeric(runtime, runtime)`), with one extra wrinkle: subtraction isn't commutative, so `numeric_literal_minus_pattern::apply` always appends lhs before rhs (matching `annium_operator_minus_numeric`'s `stack_back(1)`/`stack_back()` = lhs/rhs convention) regardless of which side, if either, was the literal being widened/materialized — `widen_for_literal_fit`'s search itself is position-agnostic (it only ever looks at "the runtime side's type" and "the literal's value"), so only the surrounding plumbing needs to keep the original left/right position, not the widening logic itself.

**`numetron::decimal` has no binary `operator-`, only binary `operator+` and unary `operator-()`** (`modules/numetron/include/numetron/basic_decimal.hpp`) — `subtract_numeric`'s `decimal` case computes `lhs + (-rhs)` instead (negating the `basic_decimal_view` operand, a cheap sign-flip, via its own unary `operator-()` in `decimal_view.hpp`, then reusing the proven binary `+`). Worth checking before assuming `numetron::integer`/`numetron::decimal` expose the C++ operator you'd naively expect for a new arithmetic op — `numetron::integer` *does* have a real binary `operator-` (`basic_integer.hpp`), so `subtract_numeric`'s `integer` case is a direct `lhs - rhs`, unlike the `decimal` case right next to it.

**`builtin_eid::isubtract` (the old integer-only `(integer,integer)~>integer` subtraction) predates this feature and is used *outside* of it**: `entities/array/array_from_iterator_make_pattern.cpp` calls `env.get(builtin_eid::isubtract)` directly (bypassing qname/pattern resolution entirely) for internal VM stack-size bookkeeping while building an array from an iterator. Reusing that qname for the new generic pattern would have put two competing arity-2 candidates in `__minus`'s overload set (the narrow typed overload and `numeric_literal_minus_pattern`, ambiguous for a plain `integer - integer` call) — so `annium_operator_minus_integer`'s registration was renamed from the public `"__minus(...)"` string to a private `"__isubtract(...)"` one (same trick as `__unary_minus` living apart from `__minus`), while its `builtin_eids_[(size_t)builtin_eid::isubtract]` slot and the C++ function itself are untouched, so the iterator-array codegen path doesn't need to change at all.

**`__multiply` (`a * b`) mirrors `__plus` exactly** (`numeric_literal_mul_pattern`, `annium_operator_mul_numeric`/`builtin_eid::multiply_numeric`/`__mul_numeric(runtime, runtime)`, registered under a brand new `builtin_qnid::multiply` qname) — multiplication is commutative like addition, so unlike `__minus` there's no operand-order concern.

`numetron::decimal` initially had no `operator*` at all (only binary `+` and unary `-`) when `multiply_numeric` was first written, so its `decimal` case originally decomposed both operands by hand via `decimal_view::significand()`/`exponent()` and reassembled the product through `numetron::integer`'s own `operator*`/`operator+`. A real `operator*(basic_decimal const&, basic_decimal_view)` has since been added directly to `basic_decimal.hpp`, so `multiply_numeric`'s `decimal` case is now the same one-line shape as `add_numeric`/`subtract_numeric`'s (`lhs.as<numetron::decimal>() * rhs.as<numetron::decimal_view>()`) — no more hand-rolled significand/exponent arithmetic.

**`*` (`ASTERISK`) needed a grammar fix before any of the above could matter, unlike `+`/`-`.** `annium.y`'s `expr` nonterminal (used by nothing active — see below) routes `ASTERISK`/`SLASH`/`PERCENT` through a `handle_call_op(...)`/`operator_type::MUL` pair that doesn't exist anywhere in the source tree (not a function, not an enum) — dead code from an abandoned earlier grammar design (`ast_terms.hpp`'s commented-out `ANNIUM_OPERATOR_ENUM` block, lines ~100-109, is the ghost of that design). The *actual* active expression grammar (the `syntax-expression` nonterminal) builds `binary_expression{ binary_operator_type::PLUS/MINUS/..., ... }` nodes directly and only recognized `ASSIGN`/`LOGIC_AND`/`LOGIC_OR`/`BIT_OR`/`BIT_AND`/`CONCAT`/`PLUS`/`MINUS`/`EQ`/`NE`/`CAST` (`ANNIUM_BINARY_OPERATOR_ENUM`, `ast_terms.hpp`) — no `MUL`, and the checked-in generated `annium.tab.cpp` has no action for `*` as a binary operator at all (confirmed by grepping it directly, not just the `.y` source). Fixed by: adding `MUL` to `ANNIUM_BINARY_OPERATOR_ENUM`; adding a `syntax-expression[larg] ASTERISK syntax-expression[rarg]` rule next to `PLUS`/`MINUS`'s (same file, "5 priority" section) building `binary_expression{ binary_operator_type::MUL, ... }`; adding `case binary_operator_type::MUL:` to `base_expression_visitor::operator()(binary_expression const&)` dispatching to the new `builtin_qnid::multiply`. The precedence machinery for this was already fully in place and unused — `%left ASTERISK SLASH PERCENT` (between `%left PLUS MINUS` and `%right DEREF EXCLPT PREFIXMINUS`) already sits at the correct multiplicative tier, and `ASTERISK` already doubles as a *unary* operator (pointer deref, `%prec DEREF` override at its own rule) the same way `MINUS` already doubles as unary negation (`%prec PREFIXMINUS`) alongside binary `MINUS` — so the prefix-vs-infix disambiguation for `*` rides on the exact same precedence-declaration trick already proven to work for `-`, not a new mechanism. **This grammar/`ast_terms.hpp` fix was deliberately left unregenerated for a time** (bison/flex regeneration is a separate, manual step) — it has since been regenerated (confirmed: `binary_operator_type::MUL` is present in the checked-in `annium.tab.cpp`), so `a * b` parses and works today.

**`/` (`SLASH`) needed a *bigger* grammar/lexer fix than `*` did.** `*`'s gap was purely a missing grammar rule — `ASTERISK` was already a fully active, `<resource_location>`-typed lexer token (used for unary pointer-deref). `SLASH` had no active lexer presence *at all*, at two separate levels: the flex *macro definition* itself (`SLASH "/"`) lived inside a dead `/* ... */`-commented block (lines ~203-248, a leftover twin of the equally-dead `handle_call_op`/`expr` grammar path) rather than in the live definitions section next to `ASTERISK`'s, and the *rule* using `{SLASH}` was similarly buried in a second, later dead comment block (lines ~468-604). Missing only the rule (and not the macro) produces a distinct flex error at build time — `annium.l:NNN: undefined definition {SLASH}` — which is how the missing macro definition surfaced after the rule alone was added first. Fixed by: (1) adding an active `SLASH "/"` macro definition to `annium.l`'s definitions section, right after `ASTERISK`'s; (2) adding `{SLASH} { variant_emplace(location); return (...token::SLASH); }` to the active `<INITIAL>` rule block, right after `ASTERISK`'s rule; (3) giving `SLASH` a `<resource_location>` token type in `annium.y` (`%token <resource_location> SLASH "\`/\`"`, previously untyped) so it can carry a location the same way `PLUS`/`MINUS`/`ASTERISK` do; (4) adding `DIV` to `ANNIUM_BINARY_OPERATOR_ENUM` (`ast_terms.hpp`); (5) a `syntax-expression[larg] SLASH syntax-expression[rarg]` rule at the same "5 priority" tier as `MUL` (`annium.y`), building `binary_expression{ binary_operator_type::DIV, ... }` and consuming `$SLASH`'s location via `std::move`, same pattern as `MUL`/`PLUS`/`MINUS`; (6) a `case binary_operator_type::DIV:` in `base_expression_visitor::operator()(binary_expression const&)` dispatching to the new `builtin_qnid::divide`. The `%left ASTERISK SLASH PERCENT` precedence declaration was already correctly in place and needed no changes — it was just as unused for `/` as it was for `*` before this. **Same deliberate deferral `*` went through: regeneration was held off for a time, then done separately** (a manual bison/flex invocation, the user's own call) — it has since happened and been confirmed (`binary_operator_type::DIV` is present in the checked-in `annium.tab.cpp`, and `arithmetic.ann`'s division tests pass), so `a / b` parses and works today, same as `a * b`.

**`__divide` (`a / b`) mirrors `__minus`'s shape** (`numeric_literal_div_pattern`, `annium_operator_div_numeric`/`builtin_eid::divide_numeric`/`__div_numeric(runtime, runtime)`, registered under a brand new `builtin_qnid::divide` qname) — division isn't commutative, so operand order is preserved exactly the way `numeric_literal_minus_pattern` preserves it, for the same reason. Two differences from `__plus`/`__minus`/`__multiply`:

1. **Two integral-kind operands give a truncating (toward zero, native C++ `/`) integral result; any floating-kind operand escalates to the corresponding float** — this happens to fall out of `strongest_numeric_type` unchanged (its integral-vs-floating exclusion rule was already exactly this rule), so no new join logic was needed, only a new `divide_numeric` doing the actual per-type `lhs.as<T>() / rhs.as<T>()` (or `float16`'s round-trip-through-`float` trick, same as the other three ops).
2. **`decimal` is rejected at runtime, but a constexpr join landing on `decimal` gets an exact-or-error check instead of a blanket rejection.** Division for `decimal` has no *general* definition — most quotients (e.g. `1 / 3`) aren't exactly representable in any finite decimal significand/exponent pair — but a fraction *does* have a finite base-10 expansion whenever its reduced denominator's only prime factors are 2 and 5, and that's decidable exactly with plain bigint arithmetic (no rounding). Since that check needs the actual operand *values*, it's only possible when both operands are already constexpr: `numeric_literal_div_pattern::try_match`'s both-constexpr branch computes `result_type = strongest_numeric_type(lhs_type, rhs_type)` same as before, and when that's `builtin_eid::decimal`, calls `try_divide_decimal_constexpr` (see point 3) instead of unconditionally failing — a compile error only fires if that returns `std::nullopt` (division by zero, or a non-terminating quotient). The literal+runtime and both-runtime branches still unconditionally reject `result_type == builtin_eid::decimal` (`type_mismatch_error`, `"runtime division is not defined for decimal"`) — there's no operand value yet to check at the point a runtime expression is compiled, so it stays undefined there (see `FUTURE_WORK.md`'s "Decide what `decimal` division should mean at runtime"). Note `result_type` can land on `decimal` even when *neither operand's own static type* is `decimal`, in all three branches — not just an exotic corner case, it's the join `i64`/`u64` get with *any* floating type: `i64`'s only safe targets are `integer`/`decimal` (per `is_always_safe_runtime_conversion`, `i64` notably has no path to `f64` the way `i32` does — 64 bits of integer precision doesn't fit exactly in a 52-bit float mantissa), so `strongest_numeric_type(i64, f32)`'s only common candidate between `{integer, decimal}` and `{f64, decimal}` is `decimal` itself. (The literal-widening path can reach the same place too: an `f64` runtime operand paired with a literal too large to represent exactly in `f64` walks past `integer` — not a safe target for `f64` — straight to `decimal`.) `divide_numeric` itself still has no `decimal` case in its `switch` at all (falls through to `THROW_INTERNAL_ERROR`) — it's only ever called with `result_type != decimal`, since the both-constexpr branch handles a `decimal` result via `try_divide_decimal_constexpr` instead, and the other two branches reject it before a call could happen.
3. **`try_divide_decimal_constexpr` (`numeric_promotion.hpp`/`.cpp`) computes the exact quotient without any long division or rounding.** Given `lhs = sig_a * 10^exp_a` and `rhs = sig_b * 10^exp_b` (a `decimal`'s actual representation — significand and base-10 exponent, see `basic_decimal.hpp`), the quotient's fractional part comes entirely from `sig_a / sig_b`; the exponents just add/subtract on top. So: reduce `sig_a/sig_b` by their `gcd` (Euclid's algorithm via `numetron::integer`'s existing `operator%`, no new numetron code); repeatedly factor 2s and 5s out of the reduced denominator, counting how many of each (`e2`, `e5`); if anything other than `1` is left in the denominator afterward, the expansion repeats forever and the function returns `std::nullopt`. Otherwise the denominator was exactly `2^e2 * 5^e5`, so multiplying the reduced numerator by the missing `2^(k-e2) * 5^(k-e5)` (`k = max(e2, e5)`, via `numetron::pow`) turns the denominator into an exact `10^k` — giving an exact integer significand over `10^k`, i.e. `result_significand * 10^(exp_a - exp_b - k)`, with sign `lhs.is_negative() != rhs.is_negative()`. Two guarded degenerate inputs: a zero divisor (would otherwise make the factor-stripping loops spin forever on `0 % 2 == 0`) returns `std::nullopt` immediately, and a zero dividend returns `decimal{0}` immediately (its `gcd` with anything is that "anything," which would trivially reduce to `1/1` but skips the general path entirely for clarity).

**One more consequence of point 2, worth knowing when writing test cases or reading a "why won't this compile" report**: a bare integer literal defaults to the arbitrary-precision `integer` type, and `integer`'s *only* safe conversion target is `decimal` (`is_always_safe_runtime_conversion`'s `integer` case) — never any fixed-width float. So `5 / 2.0` (an unannotated int literal over an unannotated float literal, itself defaulting to `decimal` — see `numeric_cast`'s bootstrap notes) or even `5 / some_f32_var` where `5` stays a bare `integer` literal will always try to join through `decimal` and get rejected. Getting a real int/float division constexpr fold requires the integer side to already be pinned to a fixed-width type first (`let x: i32 = 8; x / some_f32_literal`), exactly like `tests/test-suite/arithmetic.ann`'s `cf17`/`cf18` do.

### `divide(a, b, scale, mode)` — explicit, runtime-safe decimal division (`bootstrap.ann`)

Runtime `/` still has no definition for `decimal` (point 2 above) — a runtime quotient that doesn't terminate has no compile-time-error escape hatch to fall back on the way constexpr `/` does. `divide(a: runtime decimal, b: runtime decimal, scale: runtime u32, mode: runtime rounding_mode = .half_even) -> decimal` (`bootstrap.ann`) sidesteps this by never rejecting anything: it always rounds to at most `scale` digits after the decimal point instead. This was an explicit design choice (not a workaround) — the user considered a `#pragma`/directive-scoped default precision (like Python's `decimal.localcontext()`, MySQL's `div_precision_increment` session variable, or C's `fesetround()`) and rejected it in favor of an explicit function parameter, since ambient scoped state that silently changes what `a / b` means is exactly the kind of non-local, hard-to-reason-about behavior this language has consistently avoided elsewhere (explicit `numeric_cast`, explicit `@concept` constraints, no implicit narrowing).

`scale`'s exact meaning is "at most `scale` digits" (a cap), not "exactly `scale` digits" — the result is normalized (trailing zeros stripped) same as every other decimal arithmetic result (`add_numeric`/`multiply_numeric`'s decimal cases, `try_divide_decimal_constexpr`), so `divide(1, 4, 5)` gives `0.25`, not `0.25000`. This was a deliberate simplification, not an oversight: this codebase's `decimal` type has no way to *print* a non-significant trailing zero in the first place (no fixed-scale display mode), so an exact-padding result wouldn't be observable through `to_string` anyway — "at most" is the only meaningfully different option on the table.

`scale = 0` still returns `decimal` (never narrows to `integer`) — the return type is fixed by the function's declared signature, independent of `scale`'s actual value, which matters because `scale` can be a genuine runtime value (unlike a template parameter or constexpr argument) with no way for the type system to see through it.

**`decimal_rounding_mode` (`numeric_promotion.hpp`) mirrors `bootstrap.ann`'s `rounding_mode` enum member-for-member, by ordinal position, with no shared symbolic type** — `divide`'s body passes `to_integer(mode)` (the same generic enum-to-ordinal conversion `tests/test-suite/enums.ann` exercises) across the runtime boundary as a bare integer, and `annium_divide_decimal_rounded` (`annium_library.cpp`) reads it back with `static_cast<decimal_rounding_mode>(...)`. Keeping the two enums' declaration order in sync is a manual invariant (same category of thing as `IMPLEMENTATION_NOTES.md`'s "register a new source file in 3 places" note) — there's no compile-time check tying them together.

`divide` needed no C++-side `functional::pattern`, `builtin_qnid`, or `builtin_eid` slot at all, unlike `__plus`/`__minus`/`__multiply`/`__divide`. Those needed custom patterns because they're grammar-level *operators* (`base_expression_visitor` has to dispatch a `binary_expression` node to a specific qname by C++ enum identity, and `+`/`-` share an arity-based overload set with unary `-`) with fully generic `@numeric` parameter matching. `divide(...)` is just an ordinary named function with fixed, concrete parameter types (`decimal`, `decimal`, `u32`, `rounding_mode`) and a default argument — exactly the shape `assert_equal`/`numeric_cast`/every other `bootstrap.ann` function already handles through the normal function-matching machinery, so it's declared in `.ann` source like any of them, backed by one plain `set_builtin_extern(...)` registration (`__divide_decimal_rounded`, no `builtin_eids_[...]` slot needed since nothing in C++ calls it directly — same as `__to_i8` and its siblings).

**`divide_decimal_rounded` (`numeric_promotion.hpp`/`.cpp`) only implements `rounding_mode::half_even`; the other six values are declared (in both enums, for a stable signature) but throw `THROW_NOT_IMPLEMENTED_ERROR`.** Deliberately incremental, mirroring how `__plus`/`__minus`/`__multiply`/`__divide` were each implemented and tested before moving to the next — see `FUTURE_WORK.md`. The algorithm: scale `lhs`'s significand by `10^(exp_a - exp_b + scale)` (or scale `rhs`'s significand by `10^-(...)` if that exponent comes out negative) so the division becomes an exact-integer numerator over an exact-integer denominator; take the truncated quotient `q` and remainder `r` from that (`numetron::integer`'s existing `operator/`/`operator%`, magnitudes only — sign is reapplied at the very end via `lhs.is_negative() != rhs.is_negative()`); compare `2*r` against the denominator to find `half_even`'s tie-break (`2r < den`: round down, keep `q`; `2r > den`: round up, `q += 1`; `2r == den`: an exact tie, round to whichever of `q`/`q+1` is even); then strip trailing zeros from the result same as `try_divide_decimal_constexpr` does. Division by zero returns `std::nullopt` (same shape as `try_divide_decimal_constexpr`), which `annium_divide_decimal_rounded` turns into a real `throw exception(...)` — unlike the constexpr case, there's no compile error to report instead, this only happens at actual runtime.

## `consteval <expr>` -- forced compile-time evaluation (CTFE)

See `CONSTEVAL_CTFE_PLAN.md` for the full design and rationale; this section covers the shape the
implementation actually took, for anyone reading `ast/consteval_evaluator.*` cold.

**The operand is visited exactly once, with ordinary (unconstrained) semantics**
(`base_expression_visitor::operator()(consteval_expression const&)`, `ast/base_expression_visitor.cpp`) --
`base_expression_visitor::visit(ctx, expressions, *ce.value)`, the 3-arg overload, which leaves
`expected_result` default-constructed (`value_modifier_t::constexpr_or_runtime_value`, no forced
type). This is deliberate: it's what lets a `runtime`-only parameter materialize a constexpr
literal argument the normal way, without `consteval` needing any special-cased interaction with
overload resolution. If the operand happens to fold to a constexpr result on its own (e.g. the
whole expression turned out to reference only constexpr-foldable things), `evaluate_consteval` is
never even called -- there's nothing to run.

**The scratch function is a real, throwaway `internal_function_entity`, not hand-rolled asm.**
`evaluate_consteval` (`ast/consteval_evaluator.cpp`) builds one with an empty `entity_signature`,
inserts it into the entity registry (`environment::eregistry_insert`, purely to get it a real,
unique `entity_identifier` -- everything else about the entity is unused), assigns its `body`
field directly to the *already-produced* `syntax_expression_result::expressions` span (no
`declaration_visitor`/AST pass needed, since that span is already a fully-resolved semantic
expression list), and calls the existing `environment::compile(internal_function_entity const&)`
on it. That function's own unconditional trailing `fb.append_ret()` (see the "Unconditional" note
at its call site) is exactly what turns "push the operand's value" into a standalone `ret`-
terminated routine with no extra code needed here. The scratch entity is left as a "provision"
(the constructor's default) specifically so `annium_impl::compile`'s later
build-everything/compile-everything registry traversal skips it -- that traversal only touches
non-provision entities, and re-`build()`ing this one (which has no `sts_` at all, having bypassed
`set_body`) would silently blow its `body` away.

**Dependency materialisation walks the *already-compiled* semantic form, not the AST.**
`dependency_walker` (anonymous namespace, `consteval_evaluator.cpp`) recurses through every
branch-bearing `semantic::expression` variant (`conditional_t`, `switch_t`,
`not_empty_condition_t`, `loop_scope_t`, `return_statement`, `yield_statement`, nested
`expression_span`) and, at each `invoke_function`, force-`build()`s the callee if needed and --
only for a non-inline target -- schedules it for `environment::compile()`. It always recurses into
the callee's own body regardless of inline-ness, since an inline callee's body is what actually
ends up inside whichever function *does* get compiled (possibly the scratch block itself,
possibly one of its own non-inline callees, transitively). Compiling every collected non-inline
function before running is required, not optional: `asm_builder`'s `call` op defers to a
`pushc <const-slot>; callp` indirection when the target's address isn't known yet
(`vmasm_builder.hpp`'s `function_builder::materialize`, `case op_t::call`), and that slot is only
populated by `environment::compile()`, which nothing else has necessarily called yet at this point
in the pipeline -- `annium_impl::compile`'s own "build all, then compile all" pass runs later, for
the *outer* program.

**The same walk doubles as a "will this even run standalone" check.** The scratch entity is
frame-less (zero variables, no `pushfp`/`popfp`) by construction, so a `push_local_variable`/
`set_local_variable`/`push_by_offset{frame_bottom}` appearing directly in the operand's *own*
instructions (not inside an inlined callee's body, which gets its own pushfp/popfp-wrapped frame
at the splice site regardless of whether the caller has one) means the operand reaches into the
*enclosing* function's frame -- a value that doesn't exist yet at compile time. `dependency_walker`
tracks this via a `top_level` flag that's only true for the scratch block's own span (false the
moment it descends into any callee's body), and `evaluate_consteval` turns a hit into a clean
`basic_general_error` instead of letting it crash inside `resolve_variable_index`. The same applies
to a non-empty `syntax_expression_result::temporaries` (e.g. from short-circuit-style codegen) --
rejected outright, since materializing those would need real variable-table entries the scratch
entity doesn't have. Neither case is exercised by the motivating example or the plan's test list;
see `FUTURE_WORK.md`.

**CT-representability is checked twice, at different points, because the two failure modes are
different.** A statically-typed `object`/`callable` result (`operand.type()` already says so) is
rejected before compiling or running anything -- cheap, and covers the plan's test case
(`create_extern_object` is declared `-> object`). A result whose *static* type is `any` can't be
judged that way (see the plan's section 3.4), so the actual `blob_type` of the executed result is
checked instead, after the run, before it's handed to `make_generic_entity` -- `blob_type::object`
covers both `object` and `callable` at the wire level (a `callable` value is carried as a
`blob_type::object`-tagged handle, same as a plain host object; see `annium_invoke_callable`).
Recursing into tuple/array/struct element types, as the plan's table describes, is not implemented
-- see `FUTURE_WORK.md`.

**The compile-time host is reached through a new `environment::compile_time_host()`, not
`vm::context`'s own `penv`.** `environment` previously had no notion of a host at all -- the
`chained_host` instance lives in `annium::detail::annium_impl`, a sibling of `environment_`, and
`vm::context`'s `penv` is supplied fresh per run by whoever constructs the context (`annium_impl`,
for every real run). `evaluate_consteval` runs deep inside `declaration_visitor`, with no path back
to `annium_impl`, so `annium_impl`'s constructor now does
`environment_->set_compile_time_host(chained_host_.get())` once, right after both objects exist,
purely so `evaluate_consteval` has something to hand `vm::context`'s constructor. This is the one
piece of plumbing the plan's section 3.5 assumes is already possible but doesn't actually spell
out as a step.

**The result is deep-copied immediately, before anything else touches `vmctx`.** `smart_blob
result_blob = vmctx.stack_back(); result_blob.allocate();` happens as the very next two statements
after `bvm().run()` returns, before `vmctx.stack_pop()` even runs -- see the plan's section 3.6 for
why a returned blob can't be assumed to own its storage (`std_object::substring` returning a view
into an argument that's about to be popped is the concrete example). `.allocate()`
(`blob_result_allocate`, `invocation.hpp`) is the existing "force this blob to own independently-
allocated storage" primitive used the same way throughout `annium_environment.cpp`'s
`make_*_entity` factories.

**`blob_type` is a global-namespace enum**, not `sonia::` or `sonia::invocation::`-scoped (see its
definition in `invocation.hpp`, above any `namespace` block) -- that's why every `.cpp` in this
tree that touches it (`blob_type::object`, `blob_type::error`, ...) does so unqualified with no
`using namespace` needed.

### Guarded form: `consteval(condition) expr`

Analogous to C++'s `explicit(bool)`/`noexcept(bool)`: `condition` (required to itself be a
compile-time `bool`) decides whether `expr` is forced through CTFE at all. `true` behaves exactly
like the plain `consteval expr` above; `false` skips forcing entirely and `expr` keeps its
ordinary constexpr-or-runtime interpretation -- as if `consteval` weren't there. The motivating
case: `inline fn sqrt(@numeric) -> f64 => consteval(is_const($0)) __sqrt(runtime_cast($0));` as a
single definition, instead of the separate `runtime @numeric` / `constexpr @numeric` overload pair
`sqrt`/`log`/`floor`/`ceil`/`pow`/`round` still use in `bootstrap.ann` (that pair exists only
because each is a one-line `=>` body wrapping a plain `extern fn`, unlike `less`/`round-with-digits`
just above it in `bootstrap.ann`, which already get away with one declaration by branching on
`is_const` inside an `if`/`else` block body -- something a `=>` expression body can't do).
`consteval_expression::condition` (`ast_terms.hpp`) is null for the plain form.

**Grammar: disambiguated lexically, via a token split -- not left as a shift/reduce conflict.** The
first attempt at this feature added `CONSTEVAL OPEN_PARENTHESIS syntax-expression CLOSE_PARENTHESIS
syntax-expression` next to the plain rule (`CONSTEVAL syntax-expression`, where `syntax-expression`
already permits a parenthesized operand -- `consteval (x)` parses today, with `(x)` as the entire
operand). Both rules can derive the same prefix `CONSTEVAL OPEN_PARENTHESIS syntax-expression
CLOSE_PARENTHESIS`, and Bison confirmed a real, not just theoretical, ambiguity there
(`-Wcounterexamples`): `consteval (x) ()` could mean either "guarded, condition `x`, body the void
literal `()`" (shift) or "`(x)()` is one grouped-expression call -- call the parenthesized value `x`
(e.g. a computed callable) with no arguments -- swallowed whole as the *plain* rule's single operand"
(reduce). Bison's default shift-wins resolution gave the right answer for every real `consteval`
operand in `bootstrap.ann`/`tests/test-suite/*.ann` (none of them is a parenthesized-callable call),
but leaving a live conflict for later grammar changes to silently interact with wasn't worth it when
an actual fix was available.

The fix moves the disambiguation into the lexer instead: `annium.l` lexes a new token,
`CONSTEVAL_GUARD`, in place of plain `CONSTEVAL` only when `"consteval"` is *immediately* followed
by `"("` with no whitespace between them (`{CONSTEVAL}/{OPEN_PARENTHESIS}` -- flex trailing context,
placed before the plain `{CONSTEVAL}` rule so it wins the tie on equal-length matches). The guarded
grammar rule now starts with `CONSTEVAL_GUARD` instead of `CONSTEVAL`, so it no longer shares a
leading token with the plain rule at all -- the two productions can't conflict, because the lexer has
already committed to one meaning or the other before the parser ever sees the `(`. `consteval (x)`
(a space before the paren) always lexes as plain `CONSTEVAL` and keeps exactly its current meaning,
`(x)()` call-through-a-parenthesized-value included; only the no-space `consteval(...)` spelling
reads as the guarded form, and it always requires a trailing expression (the grammar rule demands
one) -- so the degenerate old case this would otherwise break, "the entire operand happens to be
`(x)` with nothing after, glued to `consteval` with no space," just becomes a plain parse error
instead of silently picking one of two readings; write `consteval (x);` (with a space) or drop the
redundant parens if that's genuinely what's meant. No `%prec`/`%expect` was needed -- the split
removes the conflict rather than steering Bison's resolution of it.

**Semantics: `condition` gets exactly the same const-or-evaluate treatment as `value`.** It's
visited with `expected_result_t{ .type = boolean }` (unconstrained modifier, so it resolves
constexpr on its own whenever it naturally can, e.g. `is_const($0)`), and only pushed through
`evaluate_consteval` if it didn't already fold -- the same "resolve normally first, force only if
needed" shape the plain operand uses one paragraph below it in
`base_expression_visitor::operator()(consteval_expression const&)`. The resulting native `bool`
just gates which branch of the *existing* plain-form logic runs: `forced` (from the condition, or
`true` when there's no condition at all) is OR'd into the existing
"already-const, nothing to evaluate" check, so `false` takes the exact same code path as an operand
that happened to already be constexpr on its own.

## `blob_result`'s decimal wire format (`sonia-prime/sonia/utility/invocation/invocation.hpp`)

`decimal_blob_result`/`blob_decimal_dispatch` (encode/decode pair) support two on-the-wire layouts for `blob_type::decimal`, selected by `inplace_size`:

- **Inplace** (`inplace_size == 8`): both significand and exponent fit natively — significand as `uint64_t` in `data.bp.ui64value`, exponent as `int16_t` in `data.bp.reserved.u16`, sign in `reserved0`. This is the only layout that existed before either side supported the general case.
- **Out-of-line** (`inplace_size == 0`): used whenever the significand doesn't fit `uint64_t` and/or the exponent doesn't fit `int16_t`. `payload_ptr` points at an allocated buffer holding a `[significand_limb_count, exponent_limb_count]` header (two `uint32_t`) followed by the concatenated `invocation_bigint_limb_type` (`uint64_t`) limbs — significand limbs first, then exponent limbs. Significand sign is `reserved0` (consistent with the inplace layout and with `bigint_blob_result`); exponent sign has no bit budget left in the inplace layout, so it's folded into `reserved1` instead, which this layout doesn't otherwise use.

Unlike `bigint_blob_result` (which stays `noexcept` by borrowing a pointer straight into the source `basic_integer_view`'s own backing storage, leaving allocation to the caller's later `.allocate()`), the out-of-line decimal path allocates immediately via `make_blob_result` + `blob_result_allocate(&result, true)` — the `significand` and `exponent` are two independently-located views that can't be represented as a single borrowed span, so there's no borrowing option here. The `true` (`no_inplace`) argument is load-bearing: this header+limbs buffer is only distinguishable from the inplace scalar layout by `inplace_size == 0`, so it must never get auto-placed inplace by `blob_result_allocate` even when it happens to be small enough to fit in the 14-byte inplace buffer.

Both the inplace and out-of-line decode paths hardcode `invocation_bigint_limb_type` (`uint64_t`) regardless of the template's `LimbT` — this was already true of the inplace path before the out-of-line one existed, so `decimal_blob_result`'s out-of-line branch only compiles for `LimbT == invocation_bigint_limb_type` (guarded with `if constexpr`, falling back to the pre-existing `THROW_NOT_IMPLEMENTED_ERROR` for any other limb width, so instantiating the template with a different `LimbT` still compiles as long as only the inplace path is ever hit at runtime). Every real caller in this codebase only ever uses `numetron::decimal`/`decimal_view` (`uint64_t`-limbed), so this isn't a practical restriction — but it means `bigint_blob_result`'s genericity over limb width (see its `reserved.u8.n0`/`n1` skip-bits/limb-size encoding) was deliberately *not* replicated here; extending decimal's wire format to other limb widths would need that same treatment plus a size discriminator in the header.
