# Implementation Notes

Deep-dive remarks on how specific subsystems of the Annium compiler actually work, gathered while implementing features — not a spec, not exhaustive. Referenced from `CLAUDE.md`. Add to this file (don't inline it back into `CLAUDE.md`) whenever a task turns up a non-obvious mechanism, a gotcha, or a "don't do X, it was tried and reverted" lesson.

## Stale / dead code caveat

Several places in this codebase reference APIs that no longer exist (e.g. `environment::get_builtin_function`, `qnregistry()`) or sit inside `#if 0` blocks — this is a mid-refactor codebase, not a fully-compiling reference. A grep hit is not proof a code path currently compiles; check whether it's guarded by `#if 0`/`#if` or lives in a file actually listed in the build (see "Adding a new source file" below) before treating it as a working example.

## Adding a new source file

A new `.cpp`/`.hpp` pair must be registered in **three** places or one build will silently miss it: `projects/cmake/annium/CMakeLists.txt` (`LIBRARY_SOURCES`, `.cpp` only), `projects/vs/annium/annium.vcxproj` (`ClCompile` + `ClInclude`), and `projects/vs/annium/annium.vcxproj.filters` (same, plus a `<Filter>` tag for IDE grouping).

## Function declarations & call dispatch

Every kind of callable (regular `fn`, struct constructor, `extern fn`, compiler builtins) is compiled through the same two-stage pipeline:

1. **Declaration time** (`ast/declaration_visitor.cpp`): a `fn_pure`/`fn_decl` AST node becomes a `functional::pattern` subclass (`functional/*.hpp`), registered on a `functional` object via `functional::push(pattern)` or `set_default_entity(...)`. `basic_fn_pattern` (`functional/basic_fn_pattern.*`) parses the parameter list and result expression/pattern and implements the generic `try_match`/parameter-matching machinery; concrete patterns derive from it:
   - `internal_fn_pattern` — a body-defined `fn`; lazily builds an `internal_function_entity` (inlinable).
   - `builtin_fn_pattern` (renamed from `external_fn_pattern`) — a fixed, C++-compile-time-known efn table entry (numeric `extfnid`), used for compiler builtins and `__extern_invoke` itself (registered via `environment::set_builtin_extern`). Entity is `builtin_function_entity` (renamed from `external_function_entity`).
   - `extern_fn_pattern` — a natively declared `extern fn name(...);`. Has **no entity of its own** — see below, it just synthesizes a call to the same builtin `__extern_invoke` uses.
   - `struct_fn_pattern`, `typefn_pattern` — struct-with-parameters constructors, type-level functions.
2. **Call codegen**: every call ultimately becomes a `semantic::invoke_function{entity_identifier}` semantic expression. The **single** dispatch point is `compiler_visitor_base::operator()(semantic::invoke_function const&)` in `vm/compiler_visitor.hpp` — it `dynamic_cast`s the resolved `entity` to decide how to emit code (`internal_function_entity` → `append_call`/inline expansion, `builtin_function_entity` → `append_ecall(extfnid)`). **Adding a new callable kind that needs its own codegen means adding both a new entity subclass and a new branch here** — but check first whether it can instead be expressed as a synthesized call to an *existing* builtin (see `extern_fn_pattern` below); that avoids touching this dispatcher at all.

### `extern fn` is sugar for a synthesized `__extern_invoke` call — no dedicated entity/codegen branch

`extern fn name(runtime T...) [-> R];` does **not** get its own entity or VM opcode. `extern_fn_pattern::apply()` (`functional/extern_fn_pattern.cpp`) just emits the same semantic expressions a hand-written `__extern_invoke(name, args..., argcount)` call would produce: push the fully-qualified name as a runtime string constant, push every argument (guaranteed non-const — see below), push the trailing `u32` arg count, then `invoke_function` targeting whichever of `builtin_eid::extern_invoke` / `builtin_eid::extern_invoke_void` matches whether the declared result is void — both are just the existing `builtin_function_entity` for `annium_invoke`/`annium_invoke_void` (`library/annium_library.cpp`), the same C++ functions backing `__extern_invoke` itself, now additionally captured into `builtin_eids_` (`environment::builtin_eid`) at registration time in `annium_environment.cpp` so they can be looked up directly instead of only reachable via `__extern_invoke`'s own call-matching. This means codegen for `extern fn` is just the ordinary `builtin_function_entity` → `append_ecall(extfnid)` path — no `dynamic_cast` branch, no custom stack convention to get right. (An earlier version of this feature introduced a dedicated `extern_function_entity` and a bespoke `vm::context::extern_function_call` stack convention with its own reserved-slot/pop-count bookkeeping; that turned out to be unnecessary complexity duplicating what `__extern_invoke` already does; it was removed. `vm::context::extern_function_call` still exists in `vm/annium_vm.cpp` but is unused again — don't resurrect it for this without a good reason.)

The function's runtime lookup name is every part of its qname joined with C++ `::` (no leading `::`), not just the leaf identifier — see `join_qualified_name` in `extern_fn_pattern.cpp`. A function declared inside `namespace foo` as `extern fn bar(...)` is looked up as `"foo::bar"`; a top-level one as `"bar"`.

`extern fn` parameters must be declared `runtime` explicitly (e.g. `extern fn iv_call(runtime integer);`); `declaration_visitor::operator()(fn_pure const&)` rejects any parameter whose modifier isn't `can_be_only_runtime` with a `basic_general_error`. This isn't cosmetic: `basic_fn_pattern::apply_arguments`/the matcher skip pushing any argument matched as constexpr, and `extern_fn_pattern::apply()` asserts every matched argument is non-const before pushing it — a parameter that's merely *allowed* to be constexpr (the default `constexpr_or_runtime_type` modifier) could resolve as constexpr for some call sites (e.g. a literal argument) and not others, and the receiving `annium_invoke`/`annium_invoke_void` has no way to know an argument was silently omitted. Don't try to fix this by silently forcing the modifier to `runtime_type` in `declaration_visitor` instead of rejecting — that was the first approach here and it's surprising/magic from the caller's point of view for no good reason.

When synthesizing AST nodes that aren't in the parsed source (e.g. `EXTERN FN fn-decl` in `annium.y` defaulting an unspecified result to void), prefer doing it in the **grammar action** via `ctx.make<T>(...)` (the `parser_context`'s arena, which lives for the whole parse of that resource) rather than later in `declaration_visitor`. If you do need to allocate from a later pass, use a short-lived local `arena` (`ast/arena.hpp`) that stays in scope for as long as anything might read the pointer — `arena`'s destructor frees all of its blocks, so a pointer surviving past the `arena` going out of scope is a dangling pointer (see `environment::parse_extern_fn` for that pattern: allocate and consume within the same function body).

## Compile-time `@concept` predicates (parameter matching)

`@name` on a parameter pattern (see `ANNIUM_SYNTAX.md` for the surface syntax) is a compile-time constraint: it requires a registered callable `fn name(t: typename) -> bool` and treats the parameter as matching only when calling that predicate with the candidate's type returns `true`. This was **inert until fixed** (see below) — worth knowing if you find `@X` somewhere and it doesn't seem to constrain anything; check `pattern_matcher.cpp`'s git history / this note before assuming it's dead syntax.

**Mechanism** (`functional/pattern_matcher.cpp`, `do_match_concepts`): for each `@name` in `syntax_pattern.concepts`, resolve the qname via `fn_compiler_context::lookup_qname`, synthesize a single-argument call via `call_builder` whose argument is a `syntax_expression` wrapping the candidate's `entity_identifier` directly (`entity_identifier` is itself a `syntax_expression` variant alternative — `base_expression_visitor::operator()(entity_identifier const&)` evaluates it back to that exact entity as a constexpr value, which is what makes this "pass an already-resolved value into a fresh synthetic call" trick work without needing real source syntax), dispatch it through `fn_compiler_context::find(qname_identifier, ...)` (the general by-qname-id call path, not the `builtin_qnid`-only convenience overload), and require the constexpr result to equal `true_`. All concepts on a pattern are ANDed (first failure short-circuits). On failure, returns `concept_not_satisfied_error` (`errors/concept_not_satisfied_error.*`).

**Existing predicates implementing this contract**: `is_struct` (`entities/struct/is_struct_pattern.*`), `tuple_of` (same dir, returns the tuple type rather than bool), `numeric` (`entities/literals/numeric_pattern.*`, added for the `__to_i8`.../`__to_u64` builtins' `runtime @numeric` parameters — see `library/annium_library.cpp` / `annium_environment.cpp`). All are registered under a `// TRAITS/CONCEPTS` comment block in `annium_environment.cpp`.

**Gotcha: the candidate type can itself be `typename` (not a concrete type).** When a bare/unconstrained placeholder parameter carries a concept (e.g. `bootstrap.ann`'s `inline viable fn::get(self: @is_struct, property: ...)`), calling that function with an actual *type* (not an instance) as the argument makes the type-being-checked literally `builtin_eid::typename_` — and `typename_`'s own `get_type()` is empty/invalid (there's no "type of typename" in this system; it's the top of the hierarchy). `is_struct_pattern::try_match` originally called `get_entity(env, arg_type)` unconditionally on the *derived* type-of-the-argument to `dynamic_cast` it — when that derived type came back empty, this blew up. Fix: guard with `if (!arg_er.is_const_result || arg_er.value() != env.get(builtin_eid::typename_))` before doing that lookup at all, leaving the result `false` for the `typename`-itself case. `numeric_pattern` does **not** need the same guard — it never calls `get_entity()` on the derived type; it only compares the raw `entity_identifier.value` against a fixed `builtin_eid` set via `switch`, gated by an `if (checked_type)` truthiness check, so an empty/invalid derived type just falls through to "not numeric" without ever dereferencing it. If you write a new concept predicate, prefer the `numeric_pattern` shape (raw id comparison) over `dynamic_cast`-on-`get_entity` when you can — it's shorter and structurally immune to this gotcha.

## `annium_numeric_to_*` / `__to_iN` fixed-width numeric casts

`library/annium_library.cpp`'s `annium_numeric_to_i8/ui8/i16/.../ui64` (registered as `__to_i8`.../`__to_u64` in `annium_environment.cpp`) implement `static_cast`-style truncating conversion from *any* numeric `blob_result` (fixed-width int, bigint, float16/32/64, decimal) to a specific fixed-width integer type. The truncation itself needs no bespoke bit-twiddling: `numetron::basic_integer_view<uint64_t>::operator T()` and `numetron::basic_decimal_view<uint64_t>::operator T()` (in `modules/numetron`) already implement exactly "truncate to T's width, wrap on overflow" for arbitrary-magnitude sources — the whole family reduces to dispatching on `is_floating_point(blob_type)` to pick `decimal_view` vs `integer_view`, then `static_cast<T>`. Compile-time argument validation is done via the `@numeric` concept (see above) on each builtin's signature; the C++ implementation itself doesn't need to re-validate the argument's type.
