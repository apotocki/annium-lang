# Bugfixes

A log of real bugs found in this codebase and how they were fixed — kept separate from `IMPLEMENTATION_NOTES.md` (which documents how subsystems are *intended* to work) so the two don't get tangled: this file is "here's something that was wrong and isn't anymore," that one is "here's how the mechanism works." Referenced from `CLAUDE.md`. Newest entries at the bottom.

## `is_struct_pattern` crashed when the argument itself was a `typename`

**File:** `src/annium/entities/struct/is_struct_pattern.cpp`

When a bare/unconstrained placeholder parameter carries `@is_struct` (e.g. `bootstrap.ann`'s `inline viable fn::get(self: @is_struct, property: ...)`), calling that function with an actual *type* (not an instance) as the argument makes the type-being-checked literally `builtin_eid::typename_` — and `typename_`'s own `get_type()` is empty/invalid (there's no "type of typename" in this system; it's the top of the hierarchy). `is_struct_pattern::try_match` called `get_entity(env, arg_type)` unconditionally on the *derived* type-of-the-argument to `dynamic_cast` it — when that derived type came back empty, this blew up.

**Fix:** guard with `if (!arg_er.is_const_result || arg_er.value() != env.get(builtin_eid::typename_))` before doing that lookup at all, leaving the result `false` for the `typename`-itself case.

Note for anyone writing a new `@concept` predicate: `numeric_pattern` (`entities/literals/numeric_pattern.cpp`) doesn't need this guard at all — it never calls `get_entity()` on the derived type, it only compares the raw `entity_identifier.value` against a fixed `builtin_eid` set via `switch`, gated by an `if (checked_type)` truthiness check, so an empty/invalid derived type just falls through to "not numeric" without ever dereferencing it. Prefer that shape (raw id comparison) over `dynamic_cast`-on-`get_entity` when the concept doesn't specifically need it — it's shorter and structurally immune to this bug.

## Pattern-constrained (`@concept`) parameters didn't penalize implicit-cast materialization, risking `ambiguity_error`

**Files:** `src/annium/functional/parameter_matcher.cpp`, `src/annium/functional/match_penalty.hpp/.cpp`

Surfaced by adding `numeric_cast`'s constexpr/runtime overload pair (see `IMPLEMENTATION_NOTES.md`'s `numeric_cast` section): `numeric_cast(300)` has two structurally viable overloads (a `runtime @numeric` one that materializes the constexpr literal, and a constexpr-only C++ pattern that doesn't), and both ended up with an equal `match_penalty`, i.e. `ambiguity_error`, because `constraint_matcher`'s `operator()(syntax_pattern const*)` branch (used for any `@concept`-carrying parameter) never folded the already-computed `has_cast` flag into its returned penalty — only its sibling `operator()(syntax_expression const*)` branch (plain `runtime SomeType`-style constraints) did.

**Fix:** in the pattern branch, `if (has_cast) { ++pattern_penalty.casts; }` before returning — mirrors the expression branch's `casts` accounting.

**A subtlety that broke on the first attempt:** copying the sibling branch's full return literal (`match_penalty{ .casts = has_cast, .cast_allowances = 1 }`, as the field was named at the time) instead of just the `casts` piece broke `tests/test-suite/match_priority.ann`'s `tesnfn0(42)` case (`fn tesnfn0(integer) => 1; fn tesnfn0(~integer) => 2;`, expects the pattern overload `~integer` to win). That field isn't a neutral "was this argument cast-eligible" counter — it's a fixed per-branch-kind marker: the type-expression branch always sets it to `1` (that branch always has a generic `implicit_cast` fallback available, whether or not it's used), the pattern branch always left it at `0` (a structural match either succeeds outright or fails, there's no generic cast fallback). That asymmetry *is* the tie-break `match_priority.ann` exercises (prefer a structural pattern match over a plain type-expression match when both have equal `casts`). Setting it unconditionally in the pattern branch too made both branches identical in every field whenever neither needed a cast, producing `ambiguity_error` instead of a clean win. Corrected to touch only `casts`.

**Follow-up rename:** the field was called `cast_allowances`, which reads like "a budget of permitted casts" — misleading enough that it caused the mistake above and would likely mislead the next reader too. Renamed to **`cast_capable_matches`** to describe what it actually is: a count of parameters, across the whole candidate, matched via a path capable of falling back to `implicit_cast` — not a tally of casts used (that's `casts`) and not a per-parameter allowance/budget.

**Test coverage added:** `match_priority.ann` gained `tesnfn4` (two `@numeric`-constrained overloads, `runtime` vs `constexpr`, competing on modifier alone) — this exact interaction (pattern-constrained parameter needing an implicit cast, competing against one that doesn't) had zero prior coverage, which is how the original silent-drop went unnoticed for as long as it did.

## `annium_to_integer` threw for every fixed-width integer or boolean source

**File:** `src/annium/library/annium_library.cpp`

Found while wiring up `numeric_cast(...) ~> integer`. The function had two *independent* `if` statements instead of an `if`/`else if`/`else` chain:

```cpp
if (arg->type == blob_type::boolean || is_basic_integral(arg->type)) {
    result = smart_blob{ bigint_blob_result(arg.as<numetron::integer>()) };
}
if (::is_floating_point(arg->type)) {
    ...
} else {
    THROW_INTERNAL_ERROR("cannot convert to integer: %1%"_fmt % arg);
}
```

For any fixed-width integer or boolean source, the first `if` computed a correct `result` — which was then discarded, because the second `if`'s `else` branch unconditionally threw (`is_floating_point` is false for those types). Only already-bigint (early-returned before either `if`) or floating/decimal sources ever actually worked.

**Fix:** made the second `if` an `else if`.

**Blast radius beyond `numeric_cast`:** `numeric_literal_implicit_cast_pattern::apply`'s runtime path (`entities/literals/numeric_literal_implicit_cast_pattern.cpp:474-476`) synthesizes a call to this same builtin (`builtin_eid::to_integer` / `__to_integer`) for *any* runtime value implicitly cast to `integer` — so this silently broke that general path too, for the same source types, independent of `numeric_cast`.

## `==` always returned `false` for numeric operands of different "families" (e.g. `f32 == integer`)

**File:** `src/annium/library/annium_library.cpp` (`annium_any_equal`)

Found via `assert_equal(__to_f32(w32), 300)` — `w32` is `i32`, `__to_f32(w32)` produces `f32` value `300.0`, compared against the bigint literal `300`: failed with "300 != 300" (right values, wrong verdict). Traced through `equal_pattern::apply()` (`functional/general/equal_pattern.cpp`) — for runtime operands it only materializes a constexpr side into *its own* natural type (not the other side's), so the comparison always bottoms out in `builtin_eid::equal` (`__equal`) → `annium_any_equal`, which used to delegate straight to `blob_result::operator==` (`sonia-prime`'s `invocation.hpp:1523-1538`). That operator gates each numeric branch on the *other* side being the same "family" (`::is_integral(rhs.type)` for the integral branch, `::is_floating_point(rhs.type)` for the floating/`float16`/decimal branches) — so any cross-family pair (integral vs. floating-or-decimal, either direction) short-circuits to `false` regardless of actual value, even though the `from_blob<T>` conversions needed to compare them correctly already exist and are used elsewhere (e.g. this repo's own `numeric_cast`).

**Deliberately not fixed in `blob_result::operator==` itself** (that would mean patching the `sonia-prime` submodule, a separate repository): its equality is intentionally an exact/strict comparison of same-representation values, not a numeric-value equality — conflating the two would be a semantic change to a lower-level, more widely-used primitive for the sake of one caller. Fixed instead at the Annium level, in `annium_any_equal`, as an explicit type-by-type dispatch (nested `blob_type_dispatch`, mirroring `blob_result_strict_equal_to`'s pattern in the same header — deliberately *not* hidden behind `smart_blob::as<T>()`/`from_blob<T>`, so every conversion actually taken is visible in the function itself) rather than a single blanket rule. Same-family pairs (any integer width vs. any integer width or bigint; any float width vs. any float width or decimal) are already correct *and* cheap via the untouched `blob_result::operator==`, so those are left alone entirely. Only a genuinely cross-family numeric pair (one integral-ish, one floating-ish) is dispatched by concrete type:

- If `decimal` is on either side: `numetron::decimal{ rv } == lv` — build an *owning* `numetron::decimal` from the integer side and compare directly via its `operator==`. This is the obvious approach, and the *first* one tried — it was abandoned partway through this investigation because `basic_decimal_view`'s `operator==`/`operator<=>` had a real, confirmed bug that made it silently wrong for exactly this case (see the "`basic_decimal_view::operator<=>` couldn't report equality..." entry below), and briefly replaced with a hand-rolled multiplication-based comparison (`annium_int_decimal_equal`) to route around that bug rather than fix it. That workaround has since been removed twice over: first by fixing the `operator<=>` bug itself in `numetron`, then by noticing there was an even more direct fix available — `numetron::decimal`'s own bigint constructor now normalizes at construction time (see below), so `numetron::decimal{ rv }` is simply correct, with no manual dispatch needed: overload resolution alone picks the right constructor for whatever numeric type `rv` happens to be (native int, bigint, float, or `float16`).
- Otherwise (a native `f16`/`f32`/`f64` against a fixed-width int or bigint): **not** `decimal_view` — see the next point — and **not** casting the integer to `double` either. Casting `i64`/`u64`/`bigint` to `double` loses precision above `double`'s 53 exact mantissa bits, so two genuinely *different* large integers can round to the *same* `double` and incorrectly compare equal (e.g. `9223372036854775808` = `2^63` and `9223372036854775809` = `2^63+1` both round to `2^63` as a `double`, since the ULP at that magnitude is already `2^11 = 2048`). Fixed by converting the *float* to an exact integer instead (`annium_float_int_equal`): check finite + no fractional part (anything else simply isn't equal to an integer — not a failure), then either range-check against native `int64_t`/`uint64_t` and compare natively, or — for a `numetron::basic_integer_view` (bigint) target, where there's no fixed range to check against — decompose the double into its exact binary value via `frexp`/`ldexp` (`annium_exact_bigint_from_double`: extract the 53-bit mantissa as an integer, then shift by the binary exponent using bigint multiplication or division, never losing precision) and compare that exactly against the bigint. A whole-number float converts this way exactly (it's already an integer value, just decomposed instead of rounded), unlike int→double.

**A second, more fundamental reason `decimal_view` can't be used for the float side either, caught while testing the fix above:** `basic_decimal_view`'s float constructor (`decimal_view.hpp`) builds its digits via `jkj::dragonbox::to_decimal(value, policy::trailing_zero::remove)` — dragonbox's *shortest round-trip* representation, the algorithm behind `to_string`-style formatting. "Shortest round-trip" means the shortest decimal string that parses back to the same double — **not** the double's exact mathematical value; for a double like `2^63.0`, where neighboring representable doubles are `2048` apart, dragonbox is free to (and does) return something like `9223372036854776000` instead of the exact `9223372036854775808`, since both parse back to the identical double. Comparing that against an *exact* integer `9223372036854775808` via `decimal_view`'s significand/exponent then (correctly, per `decimal_view`'s own semantics) reports them as different — which is right for `decimal_view`, but means `decimal_view` was never a valid tool for *exact*-value comparison of a float in the first place. This is why `annium_float_int_equal` converts the float to an integer instead of routing it through `decimal_view` at all. Test coverage: `casts.ann`'s `big_pow2`/`big_pow2_plus1`/`f_pow2` case, chosen specifically because `2^63` is exactly the kind of "round" value dragonbox would shorten.

**Third correction, after the first working version shipped: comparison must never throw for reasons tied to the compared values.** An intermediate exact-comparison version (decimal side especially) leaned on `THROW_INTERNAL_ERROR` for cases it considered "shouldn't happen in practice" (a bigint too wide to fit a native 64-bit integer paired with a `decimal`; an exponent too large to be realistic). That's wrong for an operator that's supposed to answer a yes/no question — `==` must always produce `true` or `false` for any two valid values, no matter how extreme, since a comparison throwing an unrelated-looking runtime error the first time someone compares a 100-digit bigint against a `decimal` is a much worse outcome than the *language* just not having arbitrary-precision numerics. The only acceptable reason to throw here is something unrelated to the *values themselves* (out of memory, etc.) — never magnitude, representability, or precision. `annium_exact_bigint_from_double`'s `frexp`/`ldexp` decomposition handles any finite double against a bigint of any size without ever rejecting it. The decimal side no longer has a value-dependent throw either, for a more fundamental reason than working around it case-by-case: see the "`basic_decimal_view` constructed non-canonically..." entry below — the root bug that motivated the value-dependent throw in the first place is now fixed in `numetron`. Test coverage: `casts.ann` gained `huge_bigint`/`huge_decimal` (a 24-digit bigint vs. `decimal`, well beyond native 64-bit range) and `huge_pow2_bigint`/`huge_pow2_f64` (`2^70` as bigint vs. `f64`, exercising `annium_exact_bigint_from_double` beyond `u64`'s range) — both cases that used to throw (in one intermediate version or another) and now compare correctly.

**Fourth correction: the `f_pow2`/`big_pow2` test itself was conceptually wrong**, independent of the implementation. It originally derived `f_pow2` via `numeric_cast(big_pow2)` and then asserted the cast result equals its source — but `numeric_cast` is an explicit, potentially-narrowing conversion that's allowed to change the value to fit the target type; asserting the *result of a lossy cast* equals its *pre-cast source* conflates "did the cast preserve this particular value" (not guaranteed) with "is `==` correct" (what the test was actually meant to check). Fixed by specifying `big_pow2`/`f_pow2` as two independently-chosen literals of the same mathematical value (`2^63`, exactly representable in both `u64` and `f64`) — the test now asserts what it means to assert, without relying on cast behavior at all.

**Fifth correction: the nested `blob_type_dispatch` in `annium_any_equal` didn't compile.** `blob_type_dispatch` instantiates its callback once per `blob_type` the *type system* knows about (`std::string_view`, `bool`, tuples, errors, ...), not just once per type that can actually reach the callback at runtime — the outer `::is_numeric(l->type) && ::is_numeric(r->type)` check only guarantees the *values* passed in are numeric, it does nothing to stop the compiler from instantiating the numeric-only body (`static_cast<double>(rv)`, `numetron::decimal{ rv }`, etc.) for e.g. `LDT = std::string_view`, where none of that compiles. **Fix:** added `is_numeric_dispatch_type_v<T>` (`is_integral_not_bool_v<T> || std::is_floating_point_v<T> || std::is_same_v<T, numetron::float16> || numetron::is_basic_integer_view_v<T> || numetron::is_basic_decimal_view_v<T>`) and wrapped the whole numeric body in `if constexpr (is_numeric_dispatch_type_v<LDT> && is_numeric_dispatch_type_v<RDT>) { ... } else { return false; }` — the same shape `blob_result_strict_equal_to` (`invocation.hpp`) already uses to gate its own per-type branches (there, `if constexpr (std::is_same_v<LDT, RDT>) { ... } else { return false; }`) before touching either operand. The `else` branch is unreachable at runtime (the outer guard already excludes non-numeric values), but still has to be there and has to type-check, since `if constexpr` only skips *instantiating* the untaken branch — it doesn't relax the requirement that *some* branch compile for every `LDT`/`RDT` combination `blob_type_dispatch` generates.

## `basic_decimal_view`/`basic_decimal` could hold or compare non-canonical (non-normalized) representations of the same value

**Files:** `modules/numetron/include/numetron/decimal_view.hpp`, `modules/numetron/include/numetron/basic_decimal.hpp` (submodule, `github.com/apotocki/numetron`), `modules/sonia-prime/sonia/utility/invocation/invocation.hpp` (submodule, `github.com/apotocki/sonia-prime`), `src/annium/library/annium_library.cpp`

Surfaced while testing an intermediate version of the `annium_any_equal` fix above (an earlier draft that routed *every* numeric comparison, including same-family ones, through `decimal_view`): `assert_equal(__to_u64(us8), 200)` (`us8` is `u8` value `200`) failed with "200 != 200". `from_blob<basic_decimal_view<LimbT>>`'s bigint branch (`invocation.hpp`) builds `decimal_view{ bigint_significand, exponent=0 }` directly from the raw bigint value, with **no normalization** — unlike its sibling branch for native integral types (`decimal_view_t{ dval }`), which strips trailing decimal zeros. So `__to_u64(us8)` (constructed via the *normalizing* native-integral path: `200` → significand `2`, exponent `2`) and the bigint literal `200` (constructed via the *non-normalizing* bigint path: significand `200`, exponent `0`) ended up as two different (but mathematically equal) representations of the same value.

**First fix attempt (reverted): normalize the bigint branch in `invocation.hpp` instead of fixing the actual comparison bug.** Took the safe in-place normalizing path only when the bigint fit a native `int64_t`/`uint64_t` (`basic_integer_view::is_fit<T>()`) and threw otherwise — reverted because it violated the "comparison must never throw for value-related reasons" rule established elsewhere in this same investigation (see the entry above), and because it was treating the symptom rather than the cause: normalizing every input can't be the general answer when `decimal_view` is a non-owning view that can't always afford to normalize (a bigint too wide for a native integer has nowhere to put a normalized significand without allocating storage that outlives the call). A second intermediate version worked around the bug entirely from the Annium side (`annium_int_decimal_equal`, a hand-rolled exact-multiplication comparison that avoided `decimal_view`'s own operators altogether) — also since removed, once the actual bug was found and fixed instead of routed around.

**The actual bugs, and the real fixes — three, related but distinct:**
1. `basic_decimal_view::operator<=>` (`decimal_view.hpp`) has a branch for comparing two views whose exponents differ, which scales the larger-exponent side's significand down via repeated division by `10`'s powers to align it with the other side, then compares. Its final comparison, `return operand >= rsa ? (0 <=> less_res) : less_res;`, only ever returned `less` or `greater` — never `equal` — because it conflated "the floor-divided quotient is `>= rsa`" with "the two values are equal after alignment." Those aren't the same thing: `floor(lsa / 10^r) >= rsa` merely means `lsa >= rsa * 10^r`, not `lsa == rsa * 10^r`.
2. Relatedly, dividing by `10^r` in chunks discarded each division's remainder without tracking it — so even the `less`/`greater` distinction was subtly wrong in one direction: if `lsa` was strictly greater than `rsa * 10^r` but by less than one full divisor step (`0 < lsa - rsa*10^r < 10^r`), the floor-divided quotient would land exactly on `rsa`, and the old code (seeing `operand >= rsa` from an exactly-equal quotient) had no way to tell that case apart from genuine equality.
   
   **Fix:** track whether *every* division performed while scaling (not just the last one) had a zero remainder (`bool exact`). At the end: if the aligned quotient equals `rsa` *and* every division along the way was exact, the values are genuinely equal (`std::strong_ordering::equal`); if the quotient equals `rsa` but any division dropped a nonzero remainder, the original value was strictly larger before rounding down, so it's `greater`, not `equal`; otherwise the existing `less`/`greater` logic (comparing the quotient to `rsa`) was already correct and is unchanged. `basic_decimal_view::operator==` (previously a separate, faster function that explicitly required both operands pre-normalized — `// expected normilized value`) is now just defined as `(lhs <=> rhs) == 0`, so it no longer carries that undocumented-until-this-bug precondition either; the common normalized/equal-exponent case still takes `operator<=>`'s existing fast path, so nothing gets slower.

3. Separately, and more fundamentally: the actual *producer* of the non-normalized bigint-sourced view was itself carrying an acknowledged, never-finished TODO. `basic_decimal`'s (the *owning* type, not the view) constructor from a `basic_integer_view` significand — `explicit basic_decimal(basic_integer_view<LimbT> s, basic_integer_view<LimbT> exp = {}, ...)`, `basic_decimal.hpp` — had a bare `// to do: normilize` comment sitting in its body and never normalized either. Unlike `basic_decimal_view` (a non-owning view, which genuinely can't always afford to compute a smaller significand — see point 1's context), `basic_decimal` *owns* its storage and can freely reallocate, so there was no structural reason for it to skip normalization; it just hadn't been implemented yet. **Fix:** the constructor now strips trailing decimal zeros from a local, owned copy of the significand before storing it (mirroring the loop the native-integral constructor and `basic_decimal_view`'s own integral/floating constructors already use), with a `!s` guard to skip the loop for a zero significand (the same infra-loop-forever hazard as the entry below — division-based trailing-zero-stripping on a value that's already zero never terminates unless explicitly special-cased).

**Why fixed here instead of routed around at the Annium level (as the first two attempts did):** these are genuine correctness/completeness bugs in `numetron`'s own types, not a design tradeoff or an intentionally-strict primitive (contrast with `blob_result::operator==`'s cross-family gate, which is deliberate design and stays untouched) — patching around them in Annium-level callers would leave them live for every other caller of `decimal_view`'s `==`/`<=>`/`<`/`>` or of `basic_decimal`'s bigint constructor, not just this one comparison. With both root causes fixed, `annium_any_equal`'s decimal-vs-integer branch (`annium_library.cpp`) is now just `numetron::decimal{ rv } == lv` — build the *owning* `numetron::decimal` from the integer side (its bigint constructor normalizes correctly now, so this works regardless of whether `rv` fits a native 64-bit integer) and compare directly; overload resolution alone picks the right `basic_decimal` constructor for whatever concrete numeric type `rv` is, no manual dispatch needed. `invocation.hpp`'s `decimal_view` bigint branch stays deliberately non-normalized (a non-owning view still can't safely normalize an oversized bigint in place), but its comment no longer needs to warn callers away from `decimal_view`'s own comparison operators, since those now handle non-normalized operands correctly too (point 1 above).

## `basic_decimal_view(integral value)` hung forever for `value == 0`

**File:** `modules/numetron/include/numetron/decimal_view.hpp` (submodule, `github.com/apotocki/numetron`)

```cpp
template <std::integral T>
inline basic_decimal_view(T value) noexcept
{
    uint8_t e = 0;
    while (!(value % 10)) {
        value /= 10; ++e;
    }
    significand_ = value;
    exponent_ = e;
}
```

This constructor strips trailing decimal zeros to normalize significand/exponent (e.g. `100` → significand `1`, exponent `2`). For `value == 0`: `0 % 10 == 0` is always true and `0 / 10 == 0` never changes `value`, so the loop never terminates — an infinite loop (hang), not a crash, so it wouldn't even show up as a clean test failure. This is on the path any integral source takes through `smart_blob::as<numetron::decimal_view>()` (`from_blob<basic_decimal_view<LimbT>>`'s integral branch constructs one directly from the value), so anything converting an integral `0` to `decimal`/`f16`/`f32`/`f64` — e.g. `__to_decimal(0)`, `numeric_cast(0) ~> f32` — would have hung.

**Fix:** skip the loop entirely when `value` is `0` (`significand_ = 0; exponent_ = 0;`), guarded with a simple `if (value) { ... }` around the existing loop.

**Negative values checked separately, no fix needed there:** since C++11, `%`/`/` truncate toward zero and the remainder's sign follows the dividend, so for any *nonzero* `value` (positive or negative) `|value|` strictly decreases each iteration where `value % 10 == 0`, and the loop always reaches either a nonzero, non-multiple-of-10 remainder or `value == 0` — the only actually-non-terminating case, now handled separately. E.g. `value = -300`: `-300 % 10 == 0` → `-30`, `e=1`; `-30 % 10 == 0` → `-3`, `e=2`; `-3 % 10 == -3` (nonzero) → stop, giving `significand_ = -3, exponent_ = 2` (`-3 × 10² = -300`), correctly.

**Test coverage added:** `casts.ann` gained `assert_equal(__to_decimal(0), 0)`, `assert_equal(__to_f32(0), 0)`, and `assert_equal(__to_decimal(-300), -300)` (negative *with* trailing zeros — actually exercises the loop body for a negative dividend, unlike the pre-existing `neg32 = -1` test which skips the loop entirely).

## `numeric_literal_equal_pattern`'s constexpr `==` converted every operand to `double` before comparing

**Files:** `src/annium/entities/literals/numeric_literal_equal_pattern.cpp`, plus a new primitive added to `modules/numetron/include/numetron/basic_integer.hpp` (submodule, `github.com/apotocki/numetron`)

Same underlying class of bug as the `annium_any_equal` entry above (naive `static_cast<double>` of an `i64`/`u64`/bigint loses precision above `double`'s 53 exact mantissa bits, so two genuinely different large integers can round to the same `double` and compare equal), but in the *other* `==` implementation: `compare_constexpr_literal_values`, used when both operands of `==` fold to constexpr numeric literals (`numeric_literal_equal_pattern::apply`). It converted every operand — integral, `f16`/`f32`/`f64`, and `decimal` alike — to `double` with a "simple approach" comment, then compared the two `double`s. Beyond the precision loss, the `f16` extraction was also internally inconsistent: the left operand read `.as<double>()` while the right operand read `.as<numetron::integer_view>()` from what is actually an `f16`-typed blob (`f16_blob_result`, `sonia-prime`'s `invocation.hpp`, stores a `numetron::float16`) — neither matches the real storage type. There was also a second, dead helper (`compare_constexpr_values`, a template never called from anywhere in the codebase) left half-implemented in the same file, including an `if constexpr (std::is_same_v<T, T>)` branch that's always true and makes every other branch in that template unreachable.

**Fix:** rewrote the function to categorize each operand (`integral` — every fixed-width int/bigint/`boolean`, all stored as `numetron::integer_view`; `f16`/`f32`/`f64`; `decimal`) and dispatch by category pair, mirroring `annium_any_equal`'s split: same-family pairs compare natively (`integer_view == integer_view`; `decimal_view == decimal_view`); `integral <-> decimal` builds an owning `numetron::decimal` from the integer side (exact, no dragonbox involved); `integral <-> floating` is the one pair that actually needs an exact cross-type primitive. Removed the dead `compare_constexpr_values` template entirely rather than trying to fix or wire it up — it was never reachable from any call site.

**The exact `integral <-> floating` primitive was added to `numetron` itself, not reimplemented locally a second time.** The runtime fix above (`annium_any_equal`) already had the right idea — `annium_exact_bigint_from_double`, a local `frexp`/`ldexp`-based exact bigint-from-double conversion, private to `annium_library.cpp` — but it was never reusable outside that one file. Added to `numetron::basic_integer` as a proper `template <std::floating_point T> explicit basic_integer(T value, ...)` constructor (throws for a non-finite or fractional `value`, since silently truncating would defeat the point of an "exact" constructor), plus a free `operator==(basic_integer_view<LimbT>, T)` for `std::floating_point T` built on top of it. This gives the same exactness guarantee as `annium_float_int_equal` used to provide, but as a general-purpose `numetron` primitive available to any caller — this constexpr fix and any future fix to the runtime cross-family path (see the entry further below: it turned out to still need one) can both use the same, single implementation instead of two parallel ad hoc ones.

**Verified with a standalone scratch program** (compiled and linked against just the `numetron` headers, outside the full project build) exercising `2^63` vs `2^63+1` against an exactly-representable `f64`, the same pair against `2^23`/`2^23+1` in `f32`, negative values, `NaN`, and `+inf` — all matched the exact (not naively-double-cast) expected results before the change was applied to `numeric_literal_equal_pattern.cpp`.

## `annium_any_equal`'s runtime cross-family path had regressed back to the lossy `int -> double` cast the `numetron` primitive above exists to avoid

**File:** `src/annium/library/annium_library.cpp`

Despite the entry above describing `annium_any_equal`'s cross-family `integral <-> floating` branch as already fixed (via a local `annium_exact_bigint_from_double`/`annium_float_int_equal` pair), the actual dispatch code cast the *integral* operand to `double` and compared doubles — exactly the lossy pattern both that entry and the one above it warn against. `annium_exact_bigint_from_double`/`annium_float_int_equal` were still present in the file but never called from anywhere: dead code sitting next to the bug it was supposed to prevent.

**Why the existing test didn't catch it:** `casts.ann` already had a `big_pow2`/`big_pow2_plus1`/`f_pow2` case for exactly this scenario, but as plain `let x: T = <literal>;` bindings it's constexpr-foldable, so `==` resolved entirely at compile time through `numeric_literal_equal_pattern` (previous entry) — a separate implementation that was already correct — and never reached the runtime `__equal` → `annium_any_equal` path at all. Wrapping (at least) one operand in `runtime_cast(...)` (`assert_equal(runtime_cast(f_pow2), runtime_cast(big_pow2))` / `assert_not_equal(runtime_cast(f_pow2), runtime_cast(big_pow2_plus1))`, added right after the existing constexpr case) forces the genuinely-runtime path and reproduced the false-positive `2^63 == 2^63+1`.

**Fix:** the `integral <-> floating` branches now compare via `numetron::integer_view{ lv } == rvdbl` / `rv == lvdbl` (or plain `lv == rvdbl` / `rv == lvdbl` when the integral side is already a `basic_integer_view`) — the same `numetron::operator==(basic_integer_view, T floating)` primitive `numeric_literal_equal_pattern` was moved onto in the entry above — instead of casting the integral side to `double`. `annium_exact_bigint_from_double`/`annium_float_int_equal` were removed entirely (fully superseded by the shared `numetron` primitive, and now truly unreachable rather than just unused); the manual `isfinite`/`trunc` pre-checks at each call site were also dropped since `numetron::operator==` already performs that check internally before decomposing the float. `#include <cmath>` was dropped from `annium_library.cpp` as nothing else in the file used it.

## `basic_decimal_view::operator==` no longer needs to route through `operator<=>`

**File:** `modules/numetron/include/numetron/decimal_view.hpp` (submodule, `github.com/apotocki/numetron`)

The "`basic_decimal_view`/`basic_decimal` could hold or compare non-canonical representations" entry above routed `operator==` through `operator<=>` specifically because, at the time, a bigint-sourced `decimal_view` (built directly in `invocation.hpp`, `decimal_blob_result`'s counterpart) could legitimately be non-normalized, and comparing un-aligned `(significand, exponent)` pairs directly would have missed equal values that only agreed after alignment.

That's no longer the situation the code is in: `from_blob<basic_decimal_view<LimbT>>` (`invocation.hpp:1246-1287`) now normalizes even its bigint branch before handing back a view — stripping trailing decimal zeros in owned scratch storage and only ever returning a normalized view (or throwing, for a bigint significand that still doesn't fit a native `int64_t` after stripping) — with the invariant spelled out explicitly in its own comment: "decimal_view is assumed always normalized." Every other producer (the integral and floating-point constructors, `blob_decimal_dispatch`'s raw read of an already-normalized `decimal`-typed blob) already upheld that invariant. With no remaining producer of an un-normalized view, `operator<=>`'s exponent-alignment machinery was solving a problem that no longer exists at the `operator==` call site.

**Fix:** reverted `operator==` to a direct `lhs.significand() == rhs.significand() && lhs.exponent() == rhs.exponent()`, `noexcept` again (the `<=>`-based version couldn't be `noexcept`, since aligning differently-scaled significands can allocate). Simpler and cheaper than routing through `<=>`, and correct precisely because every producer now guarantees normalized input — if a new non-normalizing producer of `basic_decimal_view` is ever added, it must normalize before handing the view to `operator==`, not the other way around.

## `virtual_stack_machine::traverse`'s `op::ecall` case decoded its operand starting one byte too early

**Files:** `modules/sonia-prime/sonia/utility/lang/vm.hpp`, `modules/sonia-prime/sonia/utility/lang/vm2.hpp` (submodule, `github.com/apotocki/sonia-prime`)

Found while designing a codegen-friendly annotation grammar for `op`'s dispatch shapes (each opcode needed to be classified as "reads a uint operand" / "not") and noticing `ecall`'s `case` didn't follow the same shape as every other operand-bearing opcode. Every other multi-byte opcode (`push`, `set`, the jump family, ...) does `size_t start_address = address++;` *before* calling `read_uint(address)`, so the varint operand is read starting one byte past the opcode byte itself. `op::ecall`'s case called `read_uint(address)` directly, with `address` still pointing *at* the opcode byte:

```cpp
case op::ecall:
    {
        size_t fn_index = read_uint(address);
        ftor(identity<op::ecall>, ctx, address++, fn_index);
        continue;
    }
```

`op::ecall == 31` (`0x1F`), whose high bit is clear, so `read_uint` reads that single byte, sees no continuation bit, and returns `31` immediately having advanced `address` by only one byte — treating the opcode byte itself as a complete (and wrong) one-byte varint. The real operand bytes `append_ecall` wrote for `fnindex >= 128` are left unconsumed and get reinterpreted as the start of the next instruction, desyncing decoding for the rest of the program. This only affects the long form (`fnindex >= 128`); the packed short form (opcode byte itself `>= 128`, handled in a separate branch before the `switch`) was unaffected and is why the bug went unnoticed — nothing in the test suite currently registers more than 128 external functions.

**Fix:** capture `start_address = address++` before decoding, matching every other operand-bearing case: `read_uint` now correctly starts one byte past the opcode, and `ftor` receives the opcode's own position (consistent with what `printer`'s `ecall` handler expects for display) instead of the already-advanced one.

## `environment::compile` never appended a trailing `ret` for a function body without an explicit `return`

**File:** `src/annium/annium_environment.cpp` (`environment::compile(internal_function_entity const&)`)

Found while designing a computed-goto dispatch form for the VM (see `vmop_proto.hpp`/`vm2.hpp`) that was going to rely on every function's bytecode being guaranteed to end in `op::ret`, to avoid a per-dispatch bounds check. Looked for where that guarantee is actually enforced and found it wasn't: `compiler_visitor::operator()(semantic::return_statement const&)` (`vm/compiler_visitor.hpp:431-447`) is the *only* place that emits `op::ret`, and it only fires for an explicit `return` statement in the source. `environment::compile` — the live top-level function-compilation entry point — used to have a matching "append a trailing `ret` if the body had no explicit return" step, but it was commented out:

```cpp
vmcvis(fn_ent.body);
//if (!vmcvis.local_return_position) { // no explicit return
//    fb.append_ret();
//}
fb.materialize();
```

(`vmcvis.local_return_position` doesn't exist on `compiler_visitor` any more either — a matching live block referencing it in `src/annium/annium.cpp` is itself dead, wrapped in `#if 0`.) Net effect: a `.ann` function whose body falls off the end without an explicit `return` compiled to bytecode with no terminator at all. `virtual_stack_machine::traverse()`'s `while (address < code_.size())` loop doesn't read out of bounds for this (functions are packed back-to-back in the same `code_` buffer), but it does fall through into whichever function happens to be compiled immediately after it and starts executing that function's bytecode as if it were a continuation of the current one.

**Fix:** unconditionally call `fb.append_ret()` after `vmcvis(fn_ent.body)`, instead of trying to resurrect the removed conditional. A body that already ends with an explicit `return` gets one extra, unreachable `ret` right after its own (a few harmless dead bytes); a body that doesn't now reliably gets exactly one terminator. Simpler and strictly safer than reconstructing "was the last emitted instruction already a `ret`" tracking, which no longer exists anywhere in `compiler_visitor` to build on.

## `consteval`'s scratch entity collided with a previous one in the entity registry

**File:** `src/annium/ast/consteval_evaluator.cpp` (`evaluate_consteval`)

Found by the user actually running the feature: a `consteval` expression sitting inside an `inline fn` (e.g. wiring `starts_with`'s existing `runtime`-only implementation up to a `constexpr` overload via `inline fn starts_with(self: ~ constexpr string, $prefix: constexpr string) -> bool => consteval starts_with(runtime_cast(self), runtime_cast($prefix));`) threw `"an equivalent entity has been already registered"` from `environment::eregistry_insert` the second time that `consteval` expression got evaluated for a distinct call-site match.

Root cause: the scratch `internal_function_entity` (see `IMPLEMENTATION_NOTES.md`'s `consteval` section) was constructed with a default `entity_signature{}` every time. `internal_function_entity` derives from `tagged_signatured_entity<resource_location>`, whose `equal`/`hash` key off `(get_tag() == location, *signature())` (`entities/signatured_entity.hpp`) — and two default-constructed `entity_signature{}`s always compare equal (same default `name`, empty fields, no result). So any two scratch entities built at the same `resource_location` (the `consteval` expression's own source location, which is necessarily shared across every distinct evaluation of that same AST node) collided in the registry.

**Fix:** give the scratch entity's signature a fresh `qname_identifier` (`env.new_qname_identifier()`) as its `name` — `entity_signature::name` participates in both `operator==` and `hash_value`, so this alone makes every scratch entity's signature (and therefore its full registry key) unique, independent of `loc` reuse. `entity_signature{}` became `entity_signature{ env.new_qname_identifier() }`, using the constructor that already exists for exactly this (`explicit entity_signature(qname_identifier qid) noexcept : name{ qid } {}`).

## `annium_invoke_object`/`annium_invoke_callable`/`annium_invoke`/`annium_get_object_property` could push a dangling reference onto the VM stack

**File:** `src/annium/library/annium_library.cpp`

Found by the user running `consteval.ann` under Valgrind on Linux: `consteval substring("hello", 1, 3)` produced garbage (`assert_equal` failed with `??? != ell`) even though the identical Windows build passed. Valgrind's actual complaint was three "Invalid read" reports pointing at a `memmove` inside `evaluate_consteval` (`ast/consteval_evaluator.cpp`), reading addresses described as "on thread 1's stack" — i.e. reading through a pointer into memory that belonged to some C++ function's local variables, well after that function had already returned.

Root cause, traced end to end: `std_object::substring` (`library/annium_std.cpp`) returns a plain `string_view` that's a slice of its own `target` argument — no bytes are copied. The registrar/reflection layer that turns that `string_view` return value into a `blob_result` (`string_blob_result(T&&, ...)`, `invocation.hpp`) does not copy it into owned storage either, *except* when the argument type is specifically an rvalue `std::basic_string`; a `string_view` return goes through untouched as a plain pointer+size reference. That `target` argument itself, by the time `substring` runs, is `args[0]` inside `annium_invoke_object`'s **local** `small_vector<blob_result, 16> args` — stack-resident storage. So the `smart_blob res` that `annium_invoke_object` computes is a raw pointer into its own about-to-be-destroyed stack frame. `annium_invoke_object` pushes `res` onto `ctx`'s (heap-resident) VM operand stack and returns — at which point `args` (and the bytes `res` points into) no longer exist. Nothing in `annium_invoke_object` (or the sibling functions with the identical `small_vector<blob_result, 16> args` + "invoke, then push the raw result" shape — `annium_invoke`, `annium_invoke_callable`, and `annium_get_object_property`, the last via the host object's own `get_property()` rather than an `args` array) ever calls `.allocate()`/`blob_result_allocate` on the result before handing it back.

This is not a bug `consteval` introduced — it's a pre-existing latent bug in the extern/host-invocation boundary that affects *any* execution path, `consteval` or ordinary runtime, whenever a host method returns a view into one of its own arguments (or, for `get_property`, its own transient state). It stayed unnoticed because ordinary bytecode execution typically consumes an `ecall` result via the very next instruction, before anything else reuses that exact stack region — undefined behavior that happens to read back the still-intact old bytes on most builds. `consteval`'s own path (`evaluate_consteval` unwinding back out through `bvm().run()`, `environment::compile()`, and the rest of the compiler before ever looking at the result) does enough intervening stack churn to reliably stomp it instead, and Valgrind's stack-poisoning makes the read fail loudly rather than silently returning old bytes.

**Fix:** `res.allocate()` (`resobj.allocate()` for `annium_invoke`) right after computing the result and before pushing it, in all four functions — `blob_result_allocate` is the existing "make this blob own independently-allocated storage" primitive, already unconditionally used this way throughout `annium_environment.cpp`'s `make_*_entity` factories, and is a cheap no-op for a blob that already owns its data (inplace or otherwise), so adding it unconditionally to these four call sites costs nothing in the common case and closes the dangling-reference window in the uncommon one.

`evaluate_consteval`'s own defensive `result_blob.allocate()` (added while this feature was designed, per `CONSTEVAL_CTFE_PLAN.md` section 3.6, before this root cause was tracked down) stays in place as defense-in-depth for whatever other host-returned view this class of bug might still be hiding behind — it's a no-op now that the actual source is fixed, for this specific case.

## `virtual_stack_machine::append_jt`/`append_jtx`/`append_jf`/`append_jfx` referenced enum values that don't exist

**File:** `modules/sonia-prime/sonia/utility/lang/vm2.hpp` (submodule, `github.com/apotocki/sonia-prime`) - `vm.hpp` has the identical, unfixed functions

Surfaced by the sonia-pygen `CustomBuild` step (added this session to generate `vm2.gen.hpp`), which parses `vm2.hpp` with real Clang and failed with `no member named 'jt' in 'sonia::vm::op'` (and `jtp`/`jtn`/`jf`/`jfp`/`jfn`). Those four member functions push `static_cast<uint8_t>(op::jt)` etc., but `jt`/`jtp`/`jtn`/`jf`/`jfp`/`jfn` are commented out of the `op` enum (`//jt = 4, jtp = 5, jtn = 6, //jf = 7, jfp = 8, jfn = 9,`) and never had a `traverse()` dispatch case either, in this file or `vm.hpp`. Their only real call sites are `compiler_visitor.hpp`'s `conditional_t`/`not_empty_condition_t` handling - both entirely inside `#if 0` blocks, in functions whose live body is just `THROW_NOT_IMPLEMENTED_ERROR(...)`. ## `can_convert_constexpr_value_safely`'s `decimal_view` branch let a fractional `decimal` implicitly narrow to `integer` without loss-of-precision check

**File:** `src/annium/entities/literals/numeric_promotion.hpp`

Found via `tests/test-suite/draft.ann`'s `let i8_var: i8 = 127; let i_Res: integer = i8_var + 3.5;`. Neither operand is wrapped in `runtime_cast`, so both stay constexpr: `i8_var` is a compile-time `i8` constant, and `i8_var + 3.5` folds entirely at compile time via `numeric_literal_plus_pattern`'s constexpr branch. `strongest_numeric_type(i8, decimal)` escalates to `decimal` (the only type either side safely converts into — `decimal` doesn't safely convert to anything else, per `is_always_safe_runtime_conversion`), giving a constexpr `decimal` value of `130.5`.

Assigning that to `let i_Res: integer` then goes through `numeric_literal_implicit_cast_pattern`'s constexpr path, which calls `can_convert_constexpr_value_safely(130.5, decimal, integer)` to decide whether the narrowing is lossless. In the `decimal_view` branch of that function, every fixed-width integer target (`i8`..`u64`) correctly guards on `source_val.exponent().sgn() < 0` ("has fractional part") before checking fit — but `builtin_eid::integer` had been grouped into the same `case` as the floating-point targets (`f16`/`f32`/`f64`/`decimal`), which unconditionally `return true`. So a fractional `decimal` was treated as "always safely convertible" to arbitrary-precision `integer`, silently truncating the fractional part (`130.5` → `130`) with no `numeric_cast` required — exactly the fixed-width targets' bug, just for the one target type that had been lumped in with the wrong group.

**Fix:** split `builtin_eid::integer` into its own `case`, guarded the same way as the fixed-width integer targets: `if (source_val.exponent().sgn() < 0) return false;` before returning `true`. `draft.ann`'s line now requires (and uses) an explicit `numeric_cast(i8_var + 3.5)`, matching the existing documented truncating-cast pattern in `casts.ann` (`ni5`/`ni6`, `numeric_cast(...) ~> integer` with a fractional constexpr/runtime source).

**Follow-up: the `f16`/`f32`/`f64` targets in the same `case` group had the identical problem, just harder to trigger.** `FUTURE_WORK.md` had this filed as a separate, deliberately-deferred half of the same finding: unconditionally `return true` for float targets is wrong not just for a fractional significand but for *any* value with more significant digits than the target format's mantissa can hold (e.g. a 20-digit integral `decimal` "safely" narrowing to `f32`) — a fractional part is just the easiest-to-spot special case of "doesn't fit exactly." Fixed the same way rather than leaving it deferred: each float target now does an actual round-trip check — convert `source_val` to the candidate float type (`float16_cast`/`static_cast<float>`/`static_cast<double_t>`), then rebuild a `decimal` from that float and compare it back against `source_val` via the existing `numetron::decimal == basic_decimal_view` operator (mirrors the `numetron::decimal{ rv } == lv` pattern already used in `annium_any_equal`, `annium_library.cpp`). Equal round-trip means no precision was lost; anything else means the candidate isn't actually safe. A magnitude that overflows the target float range entirely (rounds to `+-inf`) is checked with `std::isfinite` before attempting the round-trip, since `basic_decimal`'s floating-point constructor throws for a non-finite input rather than reporting "doesn't fit" — that guard is what keeps this a `bool`-returning fit check instead of an exception escaping out of `can_convert_constexpr_value_safely`.

**Follow-up 2: the `numetron::integer_view` branch (fixed-width int / bigint sources) had the exact same `return true` for `f16`/`f32`/`f64` targets, one `case` group up.** Same root cause, different `SourceValue` branch: a bigint like `2^63+1` (the same magnitude called out in `draft.ann`'s own commented-out `f_pow2`/`big_pow2_plus1` block, and in the "`annium_any_equal`'s runtime cross-family path had regressed..." entry above, both about *equality*, not this *fit-check*) would "safely" narrow to `f64` and silently round to `2^63`. Fixed with the exact-comparison primitive built for this purpose rather than another round-trip: `numetron::operator==(basic_integer_view<LimbT>, T)` for `std::floating_point T` (see the equality-follow-up entries above) already converts a whole-number `rhs` to its exact bigint value and compares directly, and already returns `false` (rather than throwing) for a non-finite or fractional `rhs` — so `source_val == static_cast<float>(source_val)` (and the `double_t`/`f16` equivalents, the latter widening through `float` first) is both the fit-check and the safety guard in one expression, no separate `isfinite` call needed here.

## `greater_eq(a, b)` was defined identically to `less_eq(a, b)`; separately, the grammar was missing the `parameter-decl` alternative `bootstrap.ann`'s own `less_eq`/`greater`/`greater_eq` needed

**Files:** `src/annium/bootstrap.ann`, `src/annium/annium.y`

Found while reviewing a newly-added `<=`/`>`/`>=` wiring (grammar tokens `LESS_EQ`/`GREATER`/`GREATER_EQ`, `base_expression_visitor.cpp`'s dispatch to `builtin_qnid::less_eq`/`greater`/`greater_eq`, and three one-line `bootstrap.ann` compositions on top of the existing `less`/`__less`). Two independent bugs surfaced here:

1. **Logic bug (`bootstrap.ann`):** `less_eq(a,b) => !less($1, $0)` (i.e. `!(b<a)`, which is `a<=b` — correct) and `greater_eq(a,b) => !less($1, $0)` were given the *exact same body*. `greater_eq(a,b)` needs `!less($0, $1)` (`!(a<b)`, i.e. `a>=b`) — as written, `greater_eq(5, 3)` evaluated `!less(3, 5)` = `!true` = `false` instead of `true`. `greater(a,b) => less($1, $0)` (`b<a`, i.e. `a>b`) was correct. **Fix:** corrected `greater_eq`'s body to `!less($0, $1)`.

2. **Grammar gap, not actually a `bootstrap.ann` bug (`annium.y`):** all three were declared as `fn less_eq(@numeric, @numeric) -> bool` — a parameter that's just a bare `@concept` list, no name, no `runtime`/`constexpr` modifier. `ANNIUM_SYNTAX.md` already documented this form as legal (`@is_struct` alone, defaulting to the `constexpr_or_runtime_type` modifier), but `parameter-decl`'s grammar rule had no alternative actually producing it — every existing unnamed-parameter alternative required either an explicit modifier (`constraint-expression-specified-mod[mod] concept-expression-list[cpts]`) or an `UNDERSCORE`/`internal-identifier` token to attach the concept list to. So `bootstrap.ann` (loaded from an embedded resource, so this surfaces at environment-init time, not as a normal compile error) failed with `syntax error, unexpected` @`, expecting` )`` right at the first `@numeric` token, before any test file even ran. An earlier pass at this fix worked around it from the `bootstrap.ann` side — splitting `less_eq`/`greater`/`greater_eq` into `runtime`/`constexpr` overload pairs, mirroring `less`'s own pair — which sidesteps the missing grammar form but leaves it missing, and needlessly duplicates three bodies that don't actually differ between the `runtime` and `constexpr` cases (unlike `less`, whose two bodies genuinely differ: real `__less` vs. `consteval __less`).

**Fix:** added the actual missing `parameter-decl` alternative to `annium.y` — `concept-expression-list[cpts] parameter-default-value-opt[default]`, right next to the `UNDERSCORE concept-expression-list-opt[cpts] ...` case it mirrors, producing an `unnamed_parameter_name` with modifier `constexpr_or_runtime_type` (see `ANNIUM_SYNTAX.md`'s `@concept` section for the full grammar-alternative rundown). This makes the bare `@numeric` form `bootstrap.ann` was already trying to use actually parse, so `less_eq`/`greater`/`greater_eq` went back to one bare-`@numeric` declaration each (the `runtime`/`constexpr` overload-pair workaround was reverted as unneeded duplication) and still fold at compile time for constexpr calls, same as `less`. Regression coverage for the logic bug (the `a==a` boundary specifically, where the swapped-argument bug is easiest to hide) added to `tests/test-suite/comparisons.ann`.
